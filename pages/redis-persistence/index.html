Redis持久化机制

# Redis 持久化机制（RDB / AOF）

Redis 数据在内存中，断电会丢。持久化负责把内存数据落地到磁盘，重启后可恢复。

# 1. 为什么要持久化

风险 说明
进程崩溃 / 机器重启 纯内存数据消失
运维误操作 需要可恢复备份
主从切换 / 扩容 常用快照做冷备与初始化

Redis 提供两种主流方案：RDB、AOF，生产常同时开启。

# 2. RDB 快照持久化

# 2.1 原理

定时将全量内存数据生成二进制快照文件（默认 dump.rdb）。

# 2.2 触发方式

方式 说明
SAVE 同步保存，阻塞主线程
BGSAVE 后台子进程保存，主线程继续服务
定时配置 如 save 900 1（900 秒内至少 1 次写则触发）
关机 正常关闭时通常会触发保存

# 2.3 优缺点

优点 缺点
文件小、恢复快 两次快照之间的数据可能丢失
适合冷备、全量备份 无法做到秒级持久化
对性能影响相对可控（BGSAVE） 数据量大时 fork 有成本

# 3. AOF 日志持久化

# 3.1 原理

记录每一条写命令日志，重启时重放日志恢复数据。

# 3.2 三种刷盘策略

策略 行为 特点
always 每条命令立刻刷盘 最安全、最慢
everysec 每秒刷盘（默认） 均衡，最多丢约 1 秒
no 由操作系统决定 最快、最不安全

# 3.3 优缺点

优点 缺点
数据丢失极少、安全性高 文件大
可接近秒级可靠 恢复比 RDB 慢
适合对丢数据敏感的场景 需要定期 AOF 重写 压缩

AOF 重写：生成更精简的命令集表达当前数据，减小文件体积。

# 4. RDB vs AOF

对比项 RDB AOF
本质 全量快照 写命令日志
文件体积 较小 较大
恢复速度 快 相对慢
数据安全性 窗口内可能丢 更高（尤其 always/everysec）
典型用途 备份、快速恢复 高可靠写路径

# 5. 生产最佳实践

  • RDB + AOF 同时开启：备份快（RDB）+ 丢数据少（AOF）
  • AOF 刷盘一般用 everysec
  • 定期检查磁盘空间与备份可用性
  • 重要业务仍要有「可重建」思路：缓存可回源，关键数据以 DB 为准
