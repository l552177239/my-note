Java 多线程与并发

# Java 多线程与并发

面向 JS + Python 背景开发者。 目标：建立「真多线程 + 共享内存」心智模型，掌握线程、线程池、同步、并发工具与常见坑；绝不把 Node 事件循环思维硬套到 Java。

# TL;DR（先看结论）

💡 一句话结论：JS（主线程）用事件循环假装并行；Java 是真并行，多个线程同时跑，共享变量必须同步。 SpringBoot 默认每个请求一条 Tomcat 线程——阻塞会占住线程，和 Node 的「异步不占线程」完全不是一回事。

  • 创建任务：Runnable / Callable；生产环境用线程池，禁止无界乱 new Thread
  • 共享可变状态三板斧：synchronized / ReentrantLock、volatile、原子类 / 并发集合
  • 线程池核心参数：核心数、最大数、队列、拒绝策略；业务池与公共池隔离
  • ConcurrentHashMap 替代并发下的 HashMap；Collections.synchronizedXxx 粗粒度少用
  • 高频坑：在请求线程里 sleep/狂算、忘记线程池关闭、锁顺序死锁、volatile 当锁用、用 HashMap 并发写、把 parallelStream 当业务线程池

# 🗺️ 本笔记知识地图

# 0. 本笔记重点（先拧扭转思维）

💡 一句话结论：在 Node 里「别阻塞事件循环」；在 Java Web 里「别把 Tomcat 线程池堵死」——怕的东西都是线程/循环被占住，但机制完全不同。

维度 JavaScript (Node) Java (典型 SpringBoot)
执行模型 单线程 + 事件循环 多线程并行
I/O 非阻塞，回调/Promise 默认阻塞 I/O（可 WebFlux）
并行计算 Worker / 多进程 多线程共享堆
共享状态 主线程少共享；Worker 传消息 堆上对象默认共享
风险焦点 堵事件循环 数据竞争、死锁、池耗尽

Python：CPython 有 GIL，多线程偏 I/O；计算密集常用多进程。Java 没有 GIL，多线程可真正吃满多核，也因此更容易写出数据竞争。

# 1. 进程 / 线程：为什么需要多线程

💡 一句话结论：进程是资源分配单位，线程是 CPU 调度单位；同进程内的线程共享堆与方法区，Java 多线程天然共享变量——这是便利，也是必须同步的原因。

# 1.1 为什么需要多线程

  • 利用多核：单线程只能用一个核，多线程才能吃满多核 CPU
  • 掩盖 I/O 等待：一个线程等磁盘/网络时，其他线程继续跑，整体吞吐提高
  • 响应性：请求处理不过来时，多线程并行 + 线程池排队，别让请求长时间被占用

# 1.2 进程 vs 线程

维度 进程 线程
资源 独立地址空间、文件描述符 共享进程堆与方法区，栈/PC 私有
切换成本 高（地址空间切换） 低
通信 IPC（管道/消息队列/共享内存） 共享内存直接读写（要同步）
隔离性 好，一个进程崩不影响其他 同进程内一个线程崩可能拖垮整个进程
创建开销 大 小

# 1.3 Java 里的线程

  • Java 平台线程与操作系统线程 1:1 映射（主流 JVM 实现），new Thread 就是在创建 OS 线程
  • 虚拟线程（JDK 21 正式）：轻量、数量可达百万级，适合大量阻塞 I/O 场景，是另一条学习线
  • 线程不是越多越好：CPU 密集 ≈ 核数；I/O 密集可稍多，但受内存与切换开销限制

# 3. 线程状态与中断

💡 一句话结论：start() 才开新线程；中断是协作式请求，不是强制杀死；stop() / suspend() / resume() 已废弃，永远别用。

# 3.1 六种状态

Java 线程的六种状态定义在 java.lang.Thread.State 枚举中

状态 含义 常见进入方式 退出/恢复
NEW 新建，尚未启动 new Thread() 后，未调用 start() 调用 start() 后进入 RUNNABLE
RUNNABLE 可运行状态，包括正在运行或就绪等待 CPU 调用 start()；从阻塞/等待/超时中恢复 被调度执行、进入阻塞/等待、运行结束
BLOCKED 阻塞，等待监视器锁 竞争 synchronized 锁失败；wait() 被唤醒后重新抢锁失败 获得监视器锁后回到 RUNNABLE
WAITING 无限期等待 Object.wait()、Thread.join()、LockSupport.park() 等无超时调用 被 notify()/notifyAll()、unpark() 唤醒，或 join 的线程结束
TIMED_WAITING 限期等待 Thread.sleep(ms)、Object.wait(timeout)、Thread.join(timeout)、LockSupport.parkNanos/parkUntil 超时、被唤醒、被中断
TERMINATED 终止 run() 正常执行完毕或抛出异常结束 不可再转换
方法 所属 是否静态 线程状态 是否释放锁 是否响应中断 唤醒方式
sleep Thread 是 TIMED_WAITING 否 是，抛 InterruptedException 超时/中断
join Thread 否 WAITING/TIMED_WAITING 释放目标线程对象锁，不释放其他 是，抛 InterruptedException 目标线程结束/超时/中断
wait Object 否 WAITING/TIMED_WAITING 释放该对象监视器锁 是，抛 InterruptedException notify/notifyAll/超时/中断
yield Thread 是 RUNNABLE 否 否 调度器
park LockSupport 是 WAITING/TIMED_WAITING 否 否，返回并保留中断标志 unpark/中断/超时
interrupt Thread 否 不直接改变状态 - - -

简单记忆

  • sleep：睡一会儿，不释放锁。
  • wait：等通知，释放对象锁，必须配合 synchronized。
  • join：等另一个线程结束。
  • yield：让一下 CPU，不释放锁。
  • park：更底层的阻塞，不释放锁，靠 unpark 唤醒。
  • interrupt：协作式中断，不是强制杀线程。

排查卡死：看线程 dump 是否大量 BLOCKED（抢锁）或 WAITING（等条件）。

# 4. JMM：主内存 / 工作内存 / happens-before

💡 一句话结论：每个线程都有「工作内存」缓存共享变量副本；不加同步，你写的值别人可能暂时看不见，指令也可能被重排序——正确性由 happens-before 规则保证。

# 4.1 为什么多线程写共享变量会出问题

count++ 看似一行，实际是 读 → 改 → 写 三步，多线程下会交错执行：

根因有三个：

问题 说明
原子性 count++ 不是一步完成，中间可能被其他线程插入
可见性 一个线程的修改可能还在工作内存，其他线程看不到
有序性 编译器/CPU 可能重排指令，破坏预期执行顺序

下面分别看 JMM 如何抽象内存、如何用 happens-before 解决这三类问题。

# 4.2 主内存 / 工作内存模型

JMM（Java Memory Model）抽象出两层内存结构：

概念 作用
主内存（Main Memory） 存放所有共享变量：实例字段、静态字段、数组元素
工作内存（Working Memory） 每个线程私有，存放它用到的共享变量副本

线程读写共享变量的流程：

  1. 从主内存 load 到工作内存；
  2. 在工作内存中读 / 改；
  3. 再 store 回主内存。

问题在于：线程之间不能直接访问对方的工作内存。不同步时，写回时机不可控 → 可见性问题；同时底层 CPU 缓存、写缓冲区、编译器优化还会引入 有序性问题。

⚠️ 注意：工作内存是 JMM 的抽象概念，并非真实存在的内存块，对应 CPU 缓存、寄存器、写缓冲区等硬件结构。

# 4.3 三大特性

特性 含义 保障手段
原子性 操作不可分割，要么全做要么不做 synchronized / Lock / 原子类 / CAS
可见性 一个线程写，其他线程能及时看到 volatile / synchronized / Lock / final / 原子类
有序性 指令不重排到破坏语义的程度 volatile / synchronized / Lock / happens-before

关键区别：

  • volatile：保证可见性 + 有序性，不保证原子性。
  • synchronized / Lock：三者都保证。
  • 原子类（AtomicInteger 等）：保证原子性 + 可见性，内部用 volatile + CAS。

# 各手段对比

手段 原子性 可见性 有序性 备注
volatile ❌ ✅ ✅ 最轻量，只适合单一读写
synchronized ✅ ✅ ✅ 重量级，可重入
Lock ✅ ✅ ✅ 灵活，可超时/中断
原子类 ✅ ✅ 部分 基于 CAS，无锁
final — ✅ ✅ 正确构造下保证
普通变量 单次读/写 ❌ ❌ 多线程下不可靠

# 4.4 happens-before 规则（够用版）

happens-before 是 JMM 的核心理论：如果 A hb B，那么 A 的执行结果对 B 可见，且 A 的执行顺序在 B 之前。

规则 含义
程序顺序规则 单线程内，前面的操作 hb 后面的操作
监视器锁规则 解锁 hb 后续对同一把锁的加锁
volatile 规则 写 volatile 变量 hb 后续读该变量
线程启动规则 Thread.start() hb 新线程中的所有动作
线程终止规则 线程所有动作 hb 其他线程从 join() 返回
线程中断规则 interrupt() hb 被中断线程检测到中断
对象终结规则 对象构造完成 hb finalize() 开始
传递性 A→B 且 B→C，则 A→C
可见性 A→B A结果对B可见

📌 happens-before 不是「时间先后」，而是可见性保证。即使物理上并行或重排，只要满足 happens-before，结果就对上层正确。

# 常见场景对应

场景 happens-before 来源
加锁后能看到前一个线程释放锁前的修改 监视器锁规则
读到 volatile 写的新值 volatile 规则
子线程能看到主线程启动前的准备数据 线程启动规则
主线程 join 后能看到子线程的结果 线程终止规则
正确发布不可变对象 final + 安全发布

# 4.5 够用规则

实际开发中，记住这三条即可：

  1. 多线程共享可变状态 → 必须有明确的 happens-before 手段
    （锁、volatile、原子类、并发集合、Thread.join 等）

  2. 不可变对象天然友好
    final 字段 + 正确发布（不逸出 this），无需额外同步。

  3. 先保证正确，再谈无锁优化
    不要过早用 volatile / CAS 替换锁，正确性优先。

64 位 JVM 下，常见状态是这样区分的：

# 6.3 Monitor：重量级锁真正的“锁对象”

Monitor 是 JVM 内部用于实现互斥的结构，通常叫 ObjectMonitor。

轻量级锁时，Mark Word 指向的是线程栈上的 Lock Record； 升级到重量级锁后，Mark Word 才会指向堆上的 Monitor。

它大致包含：

字段 作用
_owner 当前持有锁的线程
_EntryList 竞争锁失败、阻塞等待的线程队列
_WaitSet 调用 wait() 后释放锁并等待的线程队列
_recursions 重入计数，支持 synchronized 可重入
_header 保存对象头原始 Mark Word，解锁时恢复

💡 一句话结论：AQS（AbstractQueuedSynchronizer） 把状态抽成 state，把等待线程放进 CLH 队列，用 CAS + LockSupport 自己管理排队和唤醒。 Java并发包 Java.util.concurrent.locks 下的核心基础框架 AQS是 JUC 锁的地基：一个 volatile int state + 一个 CLH 变体等待队列 + 若干模板方法；ReentrantLock 是独占模式，Semaphore / CountDownLatch 是共享模式。

# 9. 线程池：ThreadPoolExecutor / ScheduledThreadPoolExecutor

💡 一句话结论：线程池复用线程、控并发、管理任务队列与拒绝策略；核心7大参数决定线程池行为；ScheduledThreadPoolExecutor 的周期任务一旦抛出未捕获异常，任务会静默取消不再执行，必须在任务内部 try-catch。

队列 特点 使用场景

# 阻塞队列核心方法

抛异常 add() remove() 满 / 空直接抛异常

# 拒绝策略完整说明

策略 行为 使用场景
AbortPolicy 默认策略：直接抛出RejectedExecutionException 业务需要感知任务失败，捕获异常降级
CallerRunsPolicy 由调用者线程执行任务，不抛异常 消费速度跟不上生产，利用调用者背压限流
DiscardPolicy 静默丢弃新任务，无异常无日志 允许丢失非核心任务场景（极少用）
DiscardOldestPolicy 丢弃队列头部等待最久任务，尝试重新提交当前任务 时效性优先，旧任务可丢弃场景

# 9.2 线程池生命周期与优雅关闭

线程池5种状态：RUNNING → SHUTDOWN → STOP → TIDYING → TERMINATED

状态 含义 进入方式
RUNNING 正常运行，接收新任务，处理队列任务 线程池初始化完成
SHUTDOWN 不再接收新任务，继续执行队列中存量任务 shutdown()
STOP 不再接收新任务，中断正在执行任务，清空等待队列 shutdownNow()
TIDYING 所有任务执行完毕，工作线程数为0，准备执行钩子terminated() 自动流转
TERMINATED 线程池彻底终止 terminated()执行完成

    pool.shutdownNow();              // 2. 等待超时，强制中断任务
}

# 9.4 ScheduledThreadPoolExecutor 定时周期线程池

⚠️ 核心坑：周期任务抛出未捕获异常，该周期任务直接静默终止，不再调度，不会主动告警。必须在任务代码内部包裹try-catch捕获所有异常+打印日志。

# 9.5 高频补充考点（面试追加）

  1. 线程复用原理：线程一旦创建，不会执行完任务就销毁；内部死循环不断从阻塞队列take()获取任务执行，实现线程复用。
  2. submit() 和 execute() 区别
    • execute(Runnable)：无返回值；任务异常直接抛出。
    • submit()：返回Future对象；异常被封装进Future，不调用future.get()异常不会抛出。
  3. 线程池参数经验设置
    • CPU密集型（大量计算，CPU打满）：核心线程数 ≈ CPU核心数 +1
    • IO密集型（DB、RPC、网络等待）：核心线程数 ≈ CPU核心数 * 2；最终以压测结果为准。
  4. allowCoreThreadTimeOut(true)：开启后核心线程空闲超时也会被回收，适合任务量波动巨大场景。

# 9.6 常见踩坑清单

  1. 使用无界队列 → OOM
  2. 定时任务不捕获异常 → 任务跑几次直接停掉
  3. 共用ForkJoin公共池执行阻塞任务 → 公共池线程耗尽，全局受影响
  4. submit提交任务，不get，异常丢失，问题难排查
  5. 忘记优雅关闭线程池，应用关闭时线程池线程阻塞，导致应用无法正常退出

# 13. 常见坑点

💡 一句话结论：池参数、锁、可见性、HashMap 并发，是线上事故四件套。

  1. new Thread 满天飞：无法控资源。
  2. 无界队列 FixedThreadPool：任务堆积 OOM。
  3. CachedThreadPool 遇突发流量：创建海量线程。
  4. 调用 run() 当 start()：根本没开新线程。
  5. volatile 做 count++：仍有竞争。
  6. 锁顺序反了：死锁。
  7. 并发写 HashMap：数据错乱。
  8. 请求线程里死循环/大计算：RT 毛刺、雪崩。
  9. Future.get() 无超时：永久卡住。
  10. 异常在线程里吞掉：任务失败毫无日志（submit 后要看 Future 或用 afterExecute）。
  11. 捕获 InterruptedException 后吞掉标志：线程从此无法被中断。
  12. 周期任务抛异常：scheduleAtFixedRate 后续周期静默取消。
