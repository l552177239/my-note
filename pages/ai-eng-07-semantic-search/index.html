07.语义搜索

# 07. 语义搜索（项目 1）

系列第 7 篇，项目 1。前 6 篇都是零件：05 篇切文本、06 篇存向量。这一篇把它们串成一条完整流水线——丢一段长文本进来，自动切分、向量化、入库；再用一句话搜出最相关的片段。 关键：这一篇不调 LLM。纯检索。先把检索质量验证好，第 9 篇接 LLM 才有意义——如果搜出来的东西就是错的，LLM 再厉害也救不回来。

# 1. 学习目标

  • 把 05（切分 + embedding）和 06（向量库）串成一条 ingest → search 流水线
  • 引入 service 层：路由变薄，业务逻辑放 app/services/
  • 检索结果带溯源信息（来源文件、块序号），为第 9 篇 RAG 引用打基础
  • 会调参：chunk_size、overlap、top_k 怎么影响搜索结果
  • 建立"检索质量好不好"的直觉判断
  • 产出物：POST /api/search/upload 喂长文本；POST /api/search/query 返回带来源的相似片段

# 2. 为什么先做纯检索

很多教程一上来就做 RAG（检索 + 生成），但 RAG 的效果好坏 80% 取决于检索质量：

用户问题 → [检索：搜到对的片段？] → [生成：LLM 基于片段回答]
                ↑                          ↑
           这步错了，后面全错          这步只能基于上面的材料

2
3

如果检索出来的片段和问题不相关，LLM 只能"一本正经地胡说八道"。所以项目 1 故意不接 LLM，先肉眼判断：搜出来的片段，到底答不答得了这个问题？

# 3. service 层：把零件串成流水线

06 篇的 /api/vector/add 要求你自己把文本切好再传 documents。实际场景里，用户丢进来的是一整篇文档，切分是自动的。把这层逻辑放到 service 里，路由只做薄薄一层。

# 3.2 新建 app/services/search_service.py

import logging

from app.core.chunking import split_text
from app.core.vector_store import add_documents, search

logger = logging.getLogger(__name__)


async def ingest_document(
    collection: str,
    raw_text: str,
    source_name: str,
    chunk_size: int = 500,
    overlap: int = 80,
) -> dict:
    """
    一条文档入库流水线：
    长文本 → 切分 → 组装 metadata（带溯源）→ 写入向量库
    """
    if not raw_text.strip():
        raise ValueError("raw_text 不能为空")

    chunks = split_text(raw_text, chunk_size, overlap)
    if not chunks:
        return {"source": source_name, "chunks_added": 0}

    # 关键：metadata 带 source 和 chunk_index，第 9 篇引用全靠它
    metadatas = [
        {"source": source_name, "chunk_index": i}
        for i in range(len(chunks))
    ]

    ids = await add_documents(collection, chunks, metadatas)
    logger.info(
        "Ingested '%s' -> %d chunks (chunk_size=%d, overlap=%d)",
        source_name, len(ids), chunk_size, overlap,
    )
    return {
        "collection": collection,
        "source": source_name,
        "chunks_added": len(ids),
    }


async def search_documents(
    collection: str,
    question: str,
    top_k: int = 5,
    where: dict | None = None,
) -> list[dict]:
    """语义搜索，返回带来源的片段。叫 search_documents 而不是 query，避免和数据库 SQL query 混淆。"""
    if not question.strip():
        return []
    return await search(collection, question, top_k, where)

# 3.3 为什么要有 service 层

路由（router）：接收 HTTP 请求、校验参数、返回 JSON
    ↓ 调用
service：业务逻辑（切分、入库、搜索）
    ↓ 调用
core（embedding/vector_store/chunking）：底层零件

到第 9 篇 RAG 时，service 层还会再包一层（检索 + 拼 prompt + 调 LLM），路由不用动。这就是 01 篇讲的"按职责分文件"。

# 4. FastAPI 接口

新建 app/routers/search.py：

from fastapi import APIRouter, HTTPException
from pydantic import BaseModel, Field

from app.services.search_service import ingest_document, search_documents

router = APIRouter(prefix="/api/search", tags=["search"])

class UploadRequest(BaseModel):
    collection: str
    raw_text: str = Field(..., min_length=1)
    source_name: str
    chunk_size: int = 500
    overlap: int = 80

class QueryRequest(BaseModel):
    collection: str
    question: str
    top_k: int = 5
    where: dict | None = None

@router.post("/upload")
async def upload(req: UploadRequest):
    try:
        result = await ingest_document(
            req.collection, req.raw_text, req.source_name,
            req.chunk_size, req.overlap,
        )
    except ValueError as e:
        raise HTTPException(status_code=422, detail=str(e))
    return result

@router.post("/query")
async def search_endpoint(req: QueryRequest):
    hits = await search_documents(req.collection, req.question, req.top_k, req.where)
    return {"hits": hits}

# 6. 调参实验：检索质量怎么调

用同一段文档，改三个参数观察结果：

# 6.1 chunk_size 太大 vs 太小

chunk_size 现象
100（太碎） 一句话被切两半，搜"退货流程"可能只命中半句，信息不完整
500（合适） 每段一个完整话题，检索命中后上下文够
2000（太大） 一段里混了退货+发票+会员，向量"失焦"，搜发票也把退货那段排前面

经验值：中文 300~500 字一段，overlap 设 chunk_size 的 15%~20%。

# 6.2 top_k 怎么选

top_k 场景
1~2 精准问答，只给 LLM 最相关的
3~5 RAG 实战常用，平衡召回和上下文长度
10+ 复杂问题，需要多段拼答案；但给 LLM 的上下文会很长

经验值：起步用 5，第 10 篇 RAG 评估时再调。

# 6.3 按来源过滤：metadata 的第一个用处

入库时每段都带了 metadata.source（来自哪个文件）。如果 collection 里存了多个文档（售后政策 + 发票说明 + 会员规则），可以只在某一个来源里搜：

{
  "collection": "faq",
  "question": "怎么退",
  "top_k": 2,
  "where": {"source": "售后政策.md"}
}

这样即使问"流程"，也不会返回发票或会员的片段。第 9 篇企业级 RAG 的权限隔离（普通员工看不到 HR 文件）就是这个机制。

# 6.4 判断检索好不好的标准

人肉看 5~10 个问题，问自己：

  1. 召回：答案相关的片段有没有出现在 top 5 里？
  2. 精确：前 3 条里有几条是真正相关的？
  3. 完整：单段够回答问题吗？还是需要相邻段？

这三个问题的答案决定了 chunk_size、overlap、top_k 怎么调。第 10 篇会用自研四项指标做自动化评估。

# 7. 产出物验收清单

  • [ ] /api/search/upload 喂一段长文档，返回 chunks_added > 0
  • [ ] /api/search/query 搜"我不喜欢能退吗"，能命中退货那段
  • [ ] 结果里带 metadata.source 和 chunk_index
  • [ ] 换 chunk_size=100 再搜一次，观察结果质量变化
  • [ ] 空文本返回 422 而不是 500
  • [ ] 能说清楚：为什么先做纯检索再做 RAG

# 8. 失败模式速查表

现象 原因 解法
搜什么都返回空 collection 名不一致 / 没入库 确认 upload 时的 collection 和 query 时一致；确认 chunks_added > 0
搜出来的片段不相关 chunk_size 太大，向量失焦 调小到 300~500
搜出来的片段语义不完整 chunk_size 太小或 overlap 太小 加大 overlap 到 chunk_size 的 20%
相关片段排很后面 embedding 模型不行 / query 和文档表述差太远 检查 embedding 模型；第 9 篇讲 query 改写
metadata 过滤后什么都搜不到 where 条件写太死或字段名拼错 先不传 where 搜，确认有结果；再逐步加过滤
upload 报 422 overlap 错误 overlap >= chunk_size 05 篇的校验在工作，调小 overlap
service 层抛 ValueError 但前端看到 500 路由没包 try/except 按 05 篇写法，ValueError 转 HTTPException(422)
改了文档重新 upload，旧版本还在 没删旧 collection 调 /api/vector/clear 清空再重新 upload
