RAG评估与优化

# 11. 记忆与多轮对话

系列第 11 篇。前面的聊天都是「一问一答」——用户说「我想退货」，模型答完，用户追问「那运费谁出」，模型已经不记得刚才说的是退货了。这一篇解决「对话连续性」：怎么存历史、怎么在上下文窗口里管理历史、历史太长怎么办。这是第 13 篇 Agent 的前置——Agent 做工具调用时天然需要记住之前调过什么。

对应代码：

  • app/core/memory.py：按 session_id 存历史、拼装 messages、滑动窗口 + 摘要
  • app/routers/chat.py：POST /api/chat/session、POST /api/chat/clear

# 1. 学习目标

  • 理解为什么单轮对话不行，什么是 session
  • 实现短期记忆：按 session_id 存取对话历史
  • 解决上下文窗口问题：滑动窗口保留最近 N 轮
  • 用 LLM 摘要压缩更早的历史
  • 知道长期记忆（用户偏好）存哪

产出物：POST /api/chat/session 带 session_id，连续对话模型能记住上文。

# 2. 为什么需要记忆

02 篇的 /api/chat 每次都只传一条 user 消息：

messages = [{"role": "user", "content": "那运费谁出"}]
1

模型看到的是孤立的一句话，不知道「那」指的是退货。多轮对话要把历史也传进去：

messages = [
    {"role": "user", "content": "我想退货"},
    {"role": "assistant", "content": "好的，请问订单号是？"},
    {"role": "user", "content": "那运费谁出"},  # 模型现在知道「那」指退货
]
1
2
3
4
5

记忆的本质：把之前的对话历史按 OpenAI messages 格式拼回去，让模型「看到」上下文。

session 就是一次连续对话的容器。同一 session_id 共享一份历史；换一个 id 就是另一段对话，互不干扰。

# 3. 短期记忆：按 session 存历史

# 3.1 内存版会话存储

学习阶段用内存 dict，重启丢。生产换 Redis（第 17 篇可观测性会提到）。

app/core/memory.py 核心结构：

from collections import defaultdict
from openai.types.chat import ChatCompletionMessageParam

# {session_id: [消息列表]}
_sessions: dict[str, list[ChatCompletionMessageParam]] = defaultdict(list)


def add_message(session_id: str, role: str, content: str):
    """存一条消息。role: user / assistant。"""
    _sessions[session_id].append({"role": role, "content": content})


def get_history(session_id: str) -> list[ChatCompletionMessageParam]:
    return _sessions.get(session_id, [])


def clear_session(session_id: str):
    _sessions.pop(session_id, None)

build_messages 负责拼最终请求：保证只有一条 system。history 里如果第一条是 system（摘要），就合并进 system_prompt，其余历史原样拼在后面，最后再加本轮 user 问题。

# 3.2 问题：历史会无限增长

聊了 50 轮，messages 有 100 条，全部塞进 context：

  • 超出模型上下文窗口（qwen2.5:14b 是 32k token）
  • 没超窗口也贵——每轮都把全部历史重发一遍，token 成本线性增长

所以要做上下文管理。

# 4. 滑动窗口：保留最近 N 轮

最简单的策略：只保留最近 N 条消息，更早的丢掉。

WINDOW_SIZE = 10  # 保留最近 10 条消息（5 轮对话）


def get_recent_history(session_id: str, window: int = WINDOW_SIZE) -> list:
    history = get_history(session_id)
    return history[-window:]  # 只取最近 N 条

  • 优点：简单、稳定、可预测
  • 缺点：很早说过的关键信息（如「我姓张」）会被丢掉

路由里真正用的是下一节的 summarize_old_history：它已经包含「保留最近 N 条」。get_recent_history 留给只要窗口、不要摘要的场景，不要和摘要函数叠着用。

# 5. 摘要压缩：把旧历史压成一段话

更好的策略：保留最近 N 轮原文，更早的历史用 LLM 压成一段摘要，开头放一条 system 消息。

async def summarize_old_history(session_id: str, keep_recent: int = 6):
    """
    如果历史超过 keep_recent 条，把更早的部分摘要成一段。
    生成摘要后必须写回存储，否则每次请求都会重复摘要，历史无限膨胀。
    """
    history = get_history(session_id)
    if len(history) <= keep_recent:
        return history

    old = history[:-keep_recent]
    recent = history[-keep_recent:]

    dialogue = "\n".join(f"{m['role']}: {m['content']}" for m in old)
    summary = await call_llm(
        messages=[
            {
                "role": "system",
                "content": "把以下对话摘要成3-5句话，保留关键事实（人名、订单号、偏好、未解决的问题）。",
            },
            {"role": "user", "content": dialogue},
        ],
        temperature=0.0,
    )

    summarized_history = [
        {"role": "system", "content": f"对话历史摘要：{summary}"}
    ] + recent

    _sessions[session_id] = summarized_history  # 写回，下次不再重复摘要
    return summarized_history

def build_messages(system_prompt, history, question):
    summary_text = ""
    if history and history[0].get("role") == "system":
        summary_text = history[0]["content"]
        history = history[1:]

    system_content = system_prompt
    if summary_text:
        system_content = f"{system_prompt}\n\n{summary_text}"

    return [
        {"role": "system", "content": system_content},
        *history,
        {"role": "user", "content": question},
    ]

对话历史摘要：用户姓张，订单号88023，想退货但担心运费问题。
user: 那运费谁出？

4

模型既知道「那」指退货，又不用把 20 轮原文都塞进去。

调用顺序（很重要）：

  1. 先 summarize_old_history（读已存历史，必要时压缩并写回）
  2. 再 build_messages + call_llm
  3. 最后才 add_message 本轮 user / assistant

本轮问题还没入库时去做摘要，避免把刚说的那句也压进旧历史。

# 6. FastAPI 接口

app/routers/chat.py（路由器前缀是 /api，所以完整路径是 /api/chat/session）：

class SessionChatRequest(BaseModel):
    session_id: str
    message: str


class ClearRequest(BaseModel):
    session_id: str


@router.post("/chat/session")
async def chat_session(req: SessionChatRequest):
    if not req.message.strip():
        raise HTTPException(status_code=422, detail="message 不能为空")

    history = await summarize_old_history(req.session_id, keep_recent=6)
    messages = build_messages("你是一个友好的助手。", history, req.message)
    answer = await call_llm(messages=messages, temperature=0.7)

    add_message(req.session_id, "user", req.message)
    add_message(req.session_id, "assistant", answer)

    return {"session_id": req.session_id, "reply": answer}


@router.post("/chat/clear")
async def clear(req: ClearRequest):
    clear_session(req.session_id)
    return {"cleared": req.session_id}

# 8. 长期记忆：用户偏好存哪

短期记忆（对话历史）和长期记忆（用户是谁、喜欢什么）是两回事：

类型 存什么 存哪 例子
短期 本次对话说了什么 内存 / Redis 「刚才说的退货」
长期 用户偏好、事实 数据库（MySQL） 「用户姓张，邮箱 a@b.com」

长期记忆在生产环境存 MySQL（现有业务库），每次对话开头从用户表里拉出来塞进 system prompt。学习阶段不展开，知道区别即可。

审计提醒：摘要压缩后，原始对话在内存里就丢了。生产如果需要审计（客服质检、合规留痕），要在摘要写回内存之前先把原始对话落盘到数据库，再用摘要替换内存里的历史。

# 9. 关键设计决策

决策 做法 原因
session_id 由谁传 前端生成 UUID，每次对话传上来 服务端不做用户体系，简单
历史存哪 内存 dict 学习阶段够用；生产换 Redis
上下文策略 滑动窗口 + 摘要 窗口简单，摘要保留关键事实
窗口大小 最近 6 条（约 3 轮） 太小忘上下文，太大费 token
摘要何时触发 len(history) > keep_recent 短对话不额外花一次 LLM
摘要温度 0.0 事实压缩，不要发挥

# 10. 产出物验收清单

  • [ ] 同一会话连续对话，模型记得上文
  • [ ] 不同 session 之间互不干扰
  • [ ] 聊 10 轮后不会爆 context（摘要在工作）
  • [ ] /api/chat/clear 清空后模型「失忆」
  • [ ] 能说清楚短期记忆和长期记忆的区别

# 11. 失败模式速查表

现象 常见原因 怎么处理
第二轮完全忘了上文 没把 history 拼进 messages；或用了单轮 /api/chat 走 /api/chat/session，检查 build_messages
第二轮记得，第十轮又忘了关键事实 只用滑动窗口，旧消息被丢掉 用 summarize_old_history，不要再叠 get_recent_history
Token 越来越贵 / 越来越慢 摘要没写回 _sessions，每轮都对全部旧历史再摘要一次 压缩后必须 _sessions[session_id] = summarized_history
出现两条 system，行为怪异 摘要是 system，业务 prompt 又是一条 system 用 build_messages 合并
摘要把本轮问题也压进去了 先 add_message 再摘要 先摘要已存历史，调完 LLM 再入库
摘要丢失订单号、人名 摘要 prompt 太泛，或温度太高 明确「保留关键事实」，temperature=0.0
换用户却串戏 前端复用了同一个 session_id 每个会话一个 UUID
重启服务后全部失忆 内存 dict，预期行为 学习阶段接受；生产换 Redis / DB
清空后仍记得 清错了 id，或请求打到另一个进程 确认 session_id；--reload 是单进程内存
message 为空仍调用模型 没校验 空字符串返回 422
并发同一 session_id 历史乱序 内存 list 无锁 学习阶段忽略；生产用 Redis 原子操作或按 session 加锁
摘要后无法质检原文 压缩覆盖了内存里的原文 写回前先落盘审计库
