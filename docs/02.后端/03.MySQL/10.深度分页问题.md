# 深度分页问题

`LIMIT offset, size` 在浅页很好用，但 `offset` 很大时（翻到第几千、几万页）会明显变慢。本文说明原因，并给出可落地的改写方案。表名以 [经典示例数据](/pages/mysql-examples/) 为准。

<!-- more -->

## 1. 什么是深度分页

普通分页（见 [DQL - 分页 LIMIT](/pages/mysql-dql/#6-分页-limit)）：

```sql
-- 第 page 页，每页 size 条
SELECT * FROM employees
ORDER BY id
LIMIT (page - 1) * size, size;

-- 例：第 10001 页，每页 10 条 → 跳过 100000 行再取 10 行
SELECT * FROM employees ORDER BY id LIMIT 100000, 10;
```

当 **偏移量很大**（例如十万、百万）时，就叫**深分页（Deep Pagination）**。业务上常见于：后台列表「跳到末页」、爬虫式翻页、导出前先扫很多页等。

---

## 2. 为什么慢

MySQL 处理 `LIMIT offset, size` 时，大致是：

1. 按 `ORDER BY` 找到满足条件的行（能走索引更好）
2. **先读过并丢弃前面的 `offset` 行**
3. 再返回后面的 `size` 行

因此：**真正返回给客户端的只有 `size` 行，但引擎已经为前面的 `offset` 行付过代价**（扫描、排序、回表等）。`offset` 越大，浪费越多，延迟越高。

可用 `EXPLAIN` 对比浅页与深页（关注扫描行数 `rows`、是否回表等）：

```sql
EXPLAIN SELECT * FROM employees ORDER BY id LIMIT 10, 10;
EXPLAIN SELECT * FROM employees ORDER BY id LIMIT 100000, 10;
```

---

## 3. 方案一：基于游标 / 上次最大 id（推荐）

思路：不记「第几页」，记**上一页最后一条的排序键**（常叫游标、seek、keyset pagination），下一页用 `WHERE` 直接定位，避免大 `OFFSET`。

### 3.1 单字段主键排序

```sql
-- 第一页
SELECT * FROM employees
ORDER BY id
LIMIT 10;

-- 下一页：上一页最后一条 id = 100（示例）
SELECT * FROM employees
WHERE id > 100
ORDER BY id
LIMIT 10;
```

接口侧通常传 `lastId`（或 `cursor`），而不是 `page`：

```text
GET /employees?size=10
GET /employees?size=10&lastId=100
```

优点：

- `id` 有索引时，可直接 **范围扫描 + LIMIT**，几乎不扫前面已翻过的行
- 大数据量下稳定，是列表「持续往下翻」的首选

注意：

- 适合「上一页 / 下一页」，**不适合随意跳到第 N 页**
- 排序键最好唯一；否则同值会漏行或重复（见 3.2）
- 中间有删除时，页码语义会变，但连续浏览一般可接受

### 3.2 多字段排序（保证唯一）

按薪资排序时，`salary` 可能重复，需带上唯一键（如 `id`）做「字典序」比较：

```sql
-- 上一页最后一条：salary = 8000, id = 50
SELECT * FROM employees
WHERE salary < 8000
   OR (salary = 8000 AND id > 50)
ORDER BY salary DESC, id ASC
LIMIT 10;
```

也可写成元组比较（MySQL 支持，语义更直观）：

```sql
SELECT * FROM employees
WHERE (salary, id) < (8000, 50)   -- 需与 ORDER BY 方向一致，这里仅示意写法
ORDER BY salary DESC, id ASC
LIMIT 10;
```

> 元组比较时，**每个字段的升降序必须与 `ORDER BY` 完全一致**，否则结果会错。拿不准就用「多条件 OR」写法。

### 3.3 适用场景

| 适合 | 不太适合 |
|------|----------|
| 信息流、消息列表、日志持续加载 | 必须展示「共 N 页 / 跳到第 500 页」 |
| App / 前端「加载更多」 | 强依赖页码的后台表格（可配合别的方案） |

## 4. 方案二：延迟关联（先取 id，再回表）

仍要按页码翻，但深页时避免「大偏移 + 宽行回表」：先在**覆盖索引**上只扫 `id`，再 `JOIN` 回原表取完整行。

```sql
-- 慢：OFFSET 大时，排序/扫描过程中可能反复回表取整行
SELECT * FROM employees
ORDER BY id
LIMIT 100000, 10;

-- 较好：子查询只拿 id（易走主键/覆盖索引），再关联取详情
SELECT e.*
FROM employees e
INNER JOIN (
    SELECT id FROM employees
    ORDER BY id
    LIMIT 100000, 10
) t ON e.id = t.id
ORDER BY e.id;
```

说明：

- **子查询仍要跳过 `offset` 行**，所以不是「免费」的，但每行只碰索引列时，成本往往远小于 `SELECT *` 深分页
- 排序字段上要有合适索引；`ORDER BY id` 时主键本身就是覆盖的
- 仍无法从根上消灭「扫描 offset 行」的成本，只是减轻回表

按业务字段排序时同理：

```sql
SELECT e.*
FROM employees e
INNER JOIN (
    SELECT id FROM employees
    ORDER BY salary DESC, id ASC
    LIMIT 100000, 10
) t ON e.id = t.id
ORDER BY e.salary DESC, e.id ASC;
```

## 5. 方案三：业务上限制深翻页

很多产品并不需要无限跳页：

- 只提供「上一页 / 下一页」，页码封顶（如最多 100 页）
- 搜索结果提示「请缩小条件」，而不是翻到第几千页
- 导出走异步任务，而不是列表深分页

这类限制往往比 SQL 技巧更有效，也更贴近真实需求。

---

## 6. 方案对比与选型

| 方案 | 能否跳页 | 深页性能 | 实现复杂度 | 推荐场景 |
|------|----------|----------|------------|----------|
| `LIMIT offset, size` | 能 | 差 | 低 | 数据量小、页码浅 |
| 游标 / `WHERE id > ?` | 一般不能 | 优 | 低～中 | 持续加载、信息流 |
| 延迟关联 | 能 | 中（优于裸 OFFSET） | 中 | 必须保留页码的后台列表 |
| 限制最大页 / 改交互 | 受限 | 优 | 低 | 多数业务列表 |

实践建议：

1. **默认用游标分页**（`lastId` / `cursor`），列表性能最稳
2. 必须页码时：浅页用普通 `LIMIT`；深页改**延迟关联**，并考虑页数上限
3. 排序列加索引；多列排序时索引顺序与 `ORDER BY` 对齐
4. 需要「总条数」时，深页场景可考虑近似计数或缓存，避免每次 `COUNT(*)` 全表扫

---

## 7. 小结

- 深分页慢，本质是 **大 `OFFSET` 强制扫描并丢弃大量行**
- 首选：**基于上次位置的条件过滤**（`WHERE id > lastId`），去掉 `OFFSET`
- 必须跳页时：用**延迟关联**减轻回表，并配合业务限制
- 分页语法基础见 [DQL - 分页 LIMIT](/pages/mysql-dql/#6-分页-limit)
