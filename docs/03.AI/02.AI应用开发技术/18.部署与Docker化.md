# 18. 部署与 Docker 化

> 系列第 18 篇，**收官**。前 17 篇跑起来需要开 3 个终端：`uv run uvicorn`、`npm run dev`、`docker compose -f langfuse.yml up`。这一篇把它们装进一个 `docker-compose.yml`——`docker compose up -d` 一条命令起全套。

<!-- more -->

---

## 1. 学习目标

- 说清楚"手动跑"和"容器化部署"的区别
- 给 FastAPI 后端写 Dockerfile（用 uv 装依赖）
- 给 React 前端写 Dockerfile（多阶段构建 + Nginx）
- 用 docker-compose 编排 Ollama / 后端 / 前端 / Langfuse
- 处理三个经典坑：容器网络、SSE 缓冲、环境变量传递
- **产出物**：`docker compose up -d` 后浏览器打开 `localhost:8080` 就能用

---

## 2. 手动跑的痛点

前 17 篇的启动流程：

```powershell
# 终端 1：Ollama
ollama serve

# 终端 2：后端
uv run uvicorn app.main:app --reload

# 终端 3：前端
cd frontend && npm run dev

# 终端 4：Langfuse
docker compose -f docker-compose.langfuse.yml up
```

问题：

| 痛点 | 现象 |
|------|------|
| 开 4 个终端 | 关一个就少一个服务 |
| 依赖本机环境 | 换台机器要重装 Python + Node + Ollama |
| 配置散落 | .env、pyproject.toml、package.json 各管各 |
| 没法上线 | 真实服务器不可能让你开 4 个终端 |

容器化的目标：一条命令起全套，环境隔离，配置集中。

---

## 3. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                   docker compose 网络                     │
│                                                          │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐             │
│  │ frontend │──▶│ backend  │──▶│  ollama  │             │
│  │  (nginx) │   │(fastapi) │   │  (LLM)   │             │
│  │  :80     │   │  :8000   │   │  :11434  │             │
│  └──────────┘   └────┬─────┘   └──────────┘             │
│      │               │                                   │
│      │               ▼                                   │
│      │         ┌──────────┐   ┌──────────┐             │
│      │         │  chroma  │   │ langfuse │             │
│      │         │ (卷持久化)│   │  :3000   │             │
│      │         └──────────┘   └──────────┘             │
│      │                                                   │
└──────┼───────────────────────────────────────────────────┘
       │
       ▼
  宿主机 :8080
```

关键点：
- 所有服务在同一个 Docker 网络，用服务名互相访问（不是 localhost）
- 只有前端暴露到宿主机 8080，其他服务只在网络内部
- Ollama 模型、Chroma 数据、Langfuse 数据都挂载卷，重启不丢

## 4. 后端 Dockerfile

`Dockerfile.backend`：

```dockerfile
FROM python:3.12-slim

# 系统依赖
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    && rm -rf /var/lib/apt/lists/*

# 装 uv
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app

# 先复制依赖清单，利用 Docker 层缓存
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# 再复制源码
COPY app ./app

# 暴露端口（文档用途，实际由 compose 映射）
EXPOSE 8000

CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

> **为什么先 COPY pyproject.toml 再 COPY 源码？** Docker 分层缓存：只要依赖清单没变，`uv sync` 这一层就命中缓存。改了源码不会触发重装依赖，构建快很多。
>
> **`uv sync --frozen`**：严格按照 `uv.lock` 安装，保证不同机器上装出来的版本完全一致。

## 5. 前端 Dockerfile

前端用多阶段构建：Node 只用来打包，最终镜像只有 Nginx + 静态文件，体积从 1GB 降到 ~50MB。

`Dockerfile.frontend`：

```dockerfile
# ---- 阶段 1：构建 ----
FROM node:20-alpine AS builder

WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build      # 产出 dist/

# ---- 阶段 2：运行 ----
FROM nginx:alpine

# 拷贝构建产物
COPY --from=builder /app/dist /usr/share/nginx/html

# 自定义 nginx 配置（SSE 必需）
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
```

`nginx.conf`：

```nginx
server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 反向代理后端 API
    location /api/ {
        proxy_pass http://backend:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        # SSE 必需：关闭缓冲
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;

        # SSE 心跳必需
        proxy_set_header Connection '';
        chunked_transfer_encoding off;
    }
}
```

SSE 三个关键配置：

| 配置 | 作用 |
|------|------|
| `proxy_buffering off` | Nginx 不缓存响应，让数据立即透传 |
| `proxy_cache off` | 不缓存 SSE 流 |
| `Connection ''` | HTTP/1.1 下关闭 keep-alive 复用，避免流被合帧 |

> 前端代码调整：之前 `api.ts` 里写死了 `http://127.0.0.1:8000`。容器化后改用相对路径：
>
> ```typescript
> const API_BASE = "";   // 空字符串 → 走同源 /api/
> // 请求变成 fetch("/api/chat/stream", ...)
> ```
>
> 本地开发时用环境变量切回完整 URL：`VITE_API_BASE=http://127.0.0.1:8000`。

## 6. docker-compose.yml

```yaml
services:
  ollama:
    image: ollama/ollama:latest
    volumes:
      - ollama-data:/root/.ollama
    # 不暴露到宿主机，只在网络内部访问
    # 如果需要从宿主机调 Ollama，加 ports: ["11434:11434"]

  backend:
    build:
      context: .
      dockerfile: Dockerfile.backend
    depends_on:
      - ollama
    environment:
      OLLAMA_HOST: http://ollama:11434        # 用服务名，不是 localhost
      CHROMA_PATH: /app/data/chroma
      LANGFUSE_HOST: http://langfuse:3000
      LANGFUSE_PUBLIC_KEY: ${LANGFUSE_PUBLIC_KEY}
      LANGFUSE_SECRET_KEY: ${LANGFUSE_SECRET_KEY}
    volumes:
      - ./data:/app/data                       # Chroma 数据持久化
    # 不需要暴露到宿主机（前端通过 nginx 反代访问）
    # 调试时可加 ports: ["8000:8000"]

  frontend:
    build:
      context: ./frontend
      dockerfile: ../Dockerfile.frontend
    depends_on:
      - backend
    ports:
      - "8080:80"                              # 宿主机 8080 → 容器 80

  langfuse-db:
    image: postgres:16
    environment:
      POSTGRES_USER: langfuse
      POSTGRES_PASSWORD: langfuse
      POSTGRES_DB: langfuse
    volumes:
      - langfuse-db-data:/var/lib/postgresql/data

  langfuse:
    image: langfuse/langfuse:2
    depends_on:
      - langfuse-db
    environment:
      DATABASE_URL: postgresql://langfuse:langfuse@langfuse-db:5432/langfuse
      NEXTAUTH_SECRET: ${LANGFUSE_NEXTAUTH_SECRET}
      SALT: ${LANGFUSE_SALT}
      NEXTAUTH_URL: http://localhost:3000
    ports:
      - "3000:3000"                            # Langfuse UI 暴露给宿主

volumes:
  ollama-data:
  langfuse-db-data:
```

`.env`（放项目根目录，不要提交到 git）：

```bash
LANGFUSE_PUBLIC_KEY=pk-lf-xxx
LANGFUSE_SECRET_KEY=sk-lf-xxx
LANGFUSE_NEXTAUTH_SECRET=change-me-to-random-string
LANGFUSE_SALT=change-me-to-another-random-string
```

`.gitignore` 加一行：

```
.env
```

## 7. 三个经典坑

### 7.1 容器内的 127.0.0.1 不是宿主机

本地跑时 `OLLAMA_HOST=http://127.0.0.1:11434` 能通。容器化后，容器里的 `127.0.0.1` 指的是容器自己，不是宿主机，也不是别的容器。

正确做法：用 compose 服务名。

```yaml
environment:
  OLLAMA_HOST: http://ollama:11434    # ✅ 服务名
  # OLLAMA_HOST: http://127.0.0.1:11434  # ❌ 容器内的自己
```

如果 Ollama 跑在宿主机（不在 compose 里），用 `host.docker.internal`：

```yaml
environment:
  OLLAMA_HOST: http://host.docker.internal:11434
```

（Linux 下需要 `extra_hosts: ["host.docker.internal:host-gateway"]`。）

### 7.2 SSE 经过 Nginx 后变成一次性返回

现象：本地开发逐字出现，容器化后整段一次性出现。

原因：Nginx 默认会缓冲响应——它在中间收完全部数据才转发给浏览器。SSE 的场景下，缓冲就等于流式失效。

修复：Nginx 配置加三行（见第 5 节的 nginx.conf）：

```nginx
proxy_buffering off;
proxy_cache off;
proxy_set_header Connection '';
```

### 7.3 CORS 在容器化后还会报错吗

不会——因为前端通过 Nginx 反代 `/api/`，浏览器看到的都是同源（`localhost:8080`），不存在跨域。

如果你选择前端直连后端（不用 nginx 反代），那 CORS 的 `allow_origins` 要加：

```python
allow_origins=["http://localhost:8080"]   # 容器化后前端地址
```

推荐还是用 Nginx 反代，省掉 CORS 一堆配置。

## 8. 跑起来

```powershell
# 1. 准备 .env
copy .env.example .env
# 填入 Langfuse 的密钥（可选，不填 Langfuse 功能禁用）

# 2. 一键起

# 4. 看状态
docker compose ps
```

浏览器：

| 服务 | 地址 |
|------|------|
| 前端聊天 | http://localhost:8080/ |
| Langfuse UI | http://localhost:3000/ |
| 后端 API 文档（可选暴露） | http://localhost:8000/docs | |

停止：

```powershell
docker compose down              # 停服务，保留卷
docker compose down -v           # 停服务 + 删数据（慎用）
```

## 9. 健康检查与启动顺序

`depends_on` 只保证容器启动顺序，不保证服务就绪。Ollama 进程起来但模型没加载完，backend 就调不通。

加 healthcheck：

```yaml
services:
  ollama:
    image: ollama/ollama:latest
    volumes:
      - ollama-data:/root/.ollama
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:11434/api/version"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s

  backend:
    depends_on:
      ollama:
        condition: service_healthy   # 等 Ollama 就绪再起 backend
```

`start_period` 告诉 Docker 前 30 秒的失败不算失败——给 Ollama 加载模型的时间。

## 10. 镜像瘦身（可选）

后端镜像默认 ~1.2GB（含 Python + 依赖）。可以优化：

**方案 A：多阶段构建**

```dockerfile
# 阶段 1：用 uv 装依赖到独立目录
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# 阶段 2：只拷贝 venv 和源码
FROM python:3.12-slim
COPY --from=builder /app/.venv /app/.venv
COPY app /app/app
ENV PATH="/app/.venv/bin:$PATH"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]
```

省掉构建工具链，能降 200MB 左右。

方案 B：换 `python:3.12-alpine`——体积更小但兼容性坑多（如 chromadb 依赖 C 编译），不推荐。

大多数情况方案 A 足够。

## 11. 生产环境 Checklist

部署到真实服务器前，至少过一遍：

| 项 | 检查 |
|----|------|
| 密钥 | .env 不提交 git；密钥通过 CI/CD 注入 |
| 端口 | 只暴露 80/443；Ollama / backend / langfuse 不直接对外 |
| HTTPS | Nginx 配 SSL；`proxy_set_header X-Forwarded-Proto https` |
| CORS | 前后端同源反代，不用开 CORS |
| 限流 | Nginx `limit_req`；后端按 IP / API Key 限流 |
| 日志 | 结构化日志落盘 + 轮转；Langfuse 保留期设好 |
| 备份 | data/（Chroma）和 langfuse-db-data 定期备份 |
| 监控 | Langfuse + Prometheus；关键指标告警 |
| 模型 | 生产用云端 API（如 DeepSeek）替代本地 Ollama，成本和延迟更可控 |

## 14. 失败模式速查表

| 现象 | 原因 | 解法 |
|------|------|------|
| 后端连不上 Ollama | 用了 127.0.0.1 | 改成服务名 `http://ollama:11434` |
| 前端 502 Bad Gateway | Nginx 反代到 backend:8000 但 backend 没起 | `docker compose logs backend` 看错；加 healthcheck |
| SSE 变成一次性返回 | Nginx 缓冲了响应 | `proxy_buffering off` |
| 重启后 Chroma 数据没了 | 没挂卷 | `volumes: ./data:/app/data` |
| Ollama 模型每次重启要重下 | 没挂卷 | `volumes: ollama-data:/root/.ollama` |
| docker compose up 卡住 | 拉模型/镜像太慢 | 等；或先 `docker compose pull` 分开拉 |
| 前端 build 失败 | package-lock.json 和 package.json 不一致 | 本地 `npm install` 后重新 commit lock 文件 |
| 端口冲突 | 宿主机 8080 / 3000 已被占用 | 改 compose 里的 `"8090:80"` |
| Langfuse 数据写不进去 | Postgres 卷权限 | `docker compose logs langfuse-db`；删卷重建 |
| 镜像体积 1GB+ | 没做多阶段构建 | 用第 10 节的方案 A |
