# 08. 文档解析与知识库入库

> 系列第 8 篇。07 篇的 upload 接口只吃纯文本，但实际业务里知识藏在 PDF、Word、Markdown 文件里。这一篇把这些文件**解析成纯文本**，清洗后接到 07 篇的入库流水线上。
> 这是 RAG 质量的隐形分水岭——解析丢字、乱码、表格变乱，后面检索和生成都救不回来。

## 1. 学习目标

- 会解析 PDF、Word、Markdown 三种最常见的文档格式
- 理解为什么"扫描版 PDF"需要 OCR（本篇不展开，知道边界即可）
- 用 FastAPI 的 `UploadFile` 做文件上传接口
- 解析 → 清洗 → 切分 → 入库，整条流水线串起来
- **产出物**：`POST /api/search/upload-file` 上传一个文件，自动解析、切分、入库

---

## 2. 文档格式现状

| 格式 | 常见来源 | 解析难度 | 本篇方案 |
|------|----------|----------|----------|
| PDF（文字版） | 产品手册、制度文件 | 中 | pdfplumber |
| PDF（扫描版） | 老合同、盖章件 | 高（要 OCR） | 本篇不做，知道边界 |
| Word (.docx) | 内部通知、方案 | 低 | python-docx |
| Markdown | wiki、技术文档 | 极低 | 直接读文本 |
| TXT | 导出的日志、纪要 | 极低 | 直接读文本 |

## 3. 装依赖

```powershell
uv add pdfplumber python-docx python-multipart
```

| 包 | 作用 |
|----|------|
| `pdfplumber` | 解析文字版 PDF，表格识别比 pypdf 好 |
| `python-docx` | 解析 .docx（注意不支持老的 .doc） |
| `python-multipart` | FastAPI 文件上传必需的表单解析库 |

> **为什么不用 PyMuPDF (fitz)？** pdfplumber 对中文 PDF 兼容性好、API 简单，学习阶段够用。生产环境如果 PDF 复杂，可以换 PyMuPDF。

## 4. 封装文档解析器

新建 `app/core/document_parser.py`：

```python
import logging
from pathlib import Path

import pdfplumber
from docx import Document as DocxDocument

logger = logging.getLogger(__name__)

MAX_FILE_SIZE = 20 * 1024 * 1024   # 20MB


def parse_pdf(file_path: str) -> str:
    """解析文字版 PDF，返回纯文本。"""
    text_parts = []
    with pdfplumber.open(file_path) as pdf:
        for page in pdf.pages:
            t = page.extract_text() or ""
            text_parts.append(t)
    return "\n".join(text_parts)


def parse_docx(file_path: str) -> str:
    """解析 .docx 文件。"""
    doc = DocxDocument(file_path)
    return "\n".join(p.text for p in doc.paragraphs if p.text.strip())


def parse_text_file(file_path: str) -> str:
    """直接读纯文本（.md/.txt）。"""
    return Path(file_path).read_text(encoding="utf-8", errors="ignore")


_PARSERS = {
    ".pdf": parse_pdf,
    ".docx": parse_docx,
    ".md": parse_text_file,
    ".txt": parse_text_file,
}


def parse_document(file_path: str) -> str:
    """根据扩展名分发解析。不支持的格式抛 ValueError。"""
    ext = Path(file_path).suffix.lower()
    if ext not in _PARSERS:
        raise ValueError(f"不支持的文件格式: {ext}（支持 .pdf/.docx/.md/.txt）")
    text = _PARSERS[ext](file_path)
    if not text.strip():
        raise ValueError("解析结果为空——可能是扫描版 PDF（需要 OCR）或文件已损坏")
    return clean_text(text)


def clean_text(text: str) -> str:
    """简单清洗：合并多余空行和空格。"""
    lines = [line.strip() for line in text.splitlines()]
    lines = [line for line in lines if line]          # 去掉空行
    return "\n".join(lines)
```

### 4.1 关于扫描版 PDF

如果 PDF 是扫描图片（没有文字层），`pdfplumber.extract_text()` 返回空字符串。这时候需要 OCR（如 Tesseract、PaddleOCR），本篇不展开。遇到空结果直接报"可能是扫描版"，不硬解。

## 5. service 层：文件入库流水线

在 `app/services/search_service.py` 里加一个函数：

```python
import asyncio
import tempfile
from pathlib import Path

from app.core.document_parser import parse_document, MAX_FILE_SIZE


async def ingest_uploaded_file(
    collection: str,
    file_content: bytes,
    filename: str,
    chunk_size: int = 500,
    overlap: int = 80,
) -> dict:
    """
    接收上传文件：保存临时文件 → 解析 → 切分 → 入库。
    """
    if len(file_content) > MAX_FILE_SIZE:
        raise ValueError(f"文件超过 {MAX_FILE_SIZE // 1024 // 1024}MB 限制")

    ext = Path(filename).suffix.lower()
    # 写到临时文件，解析完删掉
    with tempfile.NamedTemporaryFile(suffix=ext, delete=False) as tmp:
        tmp.write(file_content)
        tmp_path = tmp.name

    try:
        # pdfplumber/python-docx 都是同步阻塞调用，丢到线程池，不卡死事件循环
        raw_text = await asyncio.to_thread(parse_document, tmp_path)
        result = await ingest_document(
            collection=collection,
            raw_text=raw_text,
            source_name=filename,
            chunk_size=chunk_size,
            overlap=overlap,
        )
        result["file_type"] = ext
        result["file_size"] = len(file_content)
        return result
    finally:
        Path(tmp_path).unlink(missing_ok=True)   # 清理临时文件
```

> **为什么用 `asyncio.to_thread`？**
> 和 06 篇 Chroma 一样：pdfplumber 解析几百页 PDF 可能要几秒，这几秒里事件循环被占住，所有其他请求都排队。`to_thread` 把解析丢到线程池，主循环继续接新请求。

## 6. FastAPI 接口

在 `app/routers/search.py` 里加：

```python
from fastapi import UploadFile, File, Form

@router.post("/upload-file")
async def upload_file(
    collection: str = Form(...),
    file: UploadFile = File(...),
    chunk_size: int = Form(500),
    overlap: int = Form(80),
):
    content = await file.read()
    try:
        result = await ingest_uploaded_file(
            collection=collection,
            file_content=content,
            filename=file.filename or "unknown",
            chunk_size=chunk_size,
            overlap=overlap,
        )
    except ValueError as e:
        raise HTTPException(status_code=422, detail=str(e))
    return result
```

**注意**：文件上传不能用 JSON body，要用 `multipart/form-data`。`collection`、`chunk_size` 这些参数用 `Form(...)` 接收，文件用 `File(...)`。

## 8. 文本清洗做到什么程度

`clean_text()` 现在只做了"去空行"。实际业务中常见的脏数据：

| 脏数据 | 处理 | 什么时候做 |
|--------|------|-----------|
| 页眉页脚重复出现 | pdfplumber 按页提取时去掉 | 生产阶段再优化 |
| 表格变成乱码文本 | 用 pdfplumber 的 `extract_table()` | 涉及表格时单独处理 |
| 多余换行和空格 | 现在的 clean_text 已处理 | ✅ |
| 图片里的文字 | 需要 OCR | 本篇不做 |

**原则**：先跑通，别一开始就追求完美解析。第 10 篇 RAG 评估时会告诉你哪里需要清洗。

## 10. 失败模式速查表

| 现象 | 原因 | 解法 |
|------|------|------|
| 上传接口 422 "form data required" | 用了 JSON 而不是 multipart/form-data | 用 curl `-F` 或 Swagger 的文件选择器 |
| `python-multipart` 未安装 | 没装这个包 | `uv add python-multipart` |
| PDF 解析结果为空 | 扫描版 PDF，没有文字层 | 需要 OCR；本篇直接报 422 |
| 表格内容解析成乱码 | pdfplumber 默认按文字流提取 | 涉及表格时用 `page.extract_table()` |
| .doc 老格式报错 | python-docx 只支持 .docx | 另存为 .docx 或用 LibreOffice 转换 |
| 大文件上传超时 | 20MB 限制或 uvicorn 默认限制 | 调大 `MAX_FILE_SIZE`；生产用 nginx client_max_body_size |
| 中文乱码 | .txt 不是 UTF-8 编码 | `read_text(errors="ignore")` 已兜底；GBK 文件需要 `chardet` 检测编码 |
| 临时文件残留 | 程序在 `parse_document` 前崩溃，finally 没执行 | 确认代码在 try/finally 里；或定期清理系统 temp 目录 |
| 上传大文件时其他接口全部卡死 | pdfplumber 同步解析阻塞了事件循环 | 用 `asyncio.to_thread(parse_document, tmp_path)` 包装 |
