# 15. Agent Skills

> 系列第 15 篇。14 篇解决了"工具怎么接"——MCP 让工具可以跨进程、跨语言。但工具仍然是**原子操作**：查订单、取消订单、发短信。真实业务里的任务往往是**一整套固定流程**："处理退货"= 查订单 → 判断状态 → 取消 → 通知用户。
> 如果让 LLM 每步临场决策，每次结果都不一样。这一篇引入 **Skill（技能）**：把固定流程打包成一个可复用的能力单元，LLM 只负责触发，内部步骤写死。

## 1. 学习目标

- 理解 Tool / Skill / Agent 三个层次的区别
- 说清楚什么时候该用 Skill，什么时候该用 ReAct
- 实现一个 Skill 基类 + 注册机制
- 把"处理退货"打包成一个 Skill，内部串联多个工具
- 让第 13 篇的 Agent 识别并调用 Skill
- **产出物**：`POST /api/agent/chat-skill`，用户说"帮我退掉订单88024"，Agent 自动触发 `process_refund` Skill

---

## 2. 工具、技能、Agent：三个层次

前 14 篇我们其实一直在三个层次之间穿梭，但没明确拆开：

| 层次 | 单元 | 例子 | 决策粒度 |
|------|------|------|----------|
| **Tool（工具）** | 原子操作 | `get_order_status`、`cancel_order` | LLM 每步临场决定调哪个 |
| **Skill（技能）** | 固定流程 | "处理退货"、"催单"、"改地址" | LLM 只决定用不用 + 传参数 |
| **Agent** | 自主循环 | 通用助手，多步推理 | LLM 自主规划整个任务 |

打个比方：

- **Tool 是螺丝刀**——什么时候用、怎么用，靠 LLM 现场判断
- **Skill 是宜家说明书**——步骤固定，照着做就行，LLM 只负责"要不要组装这个柜子"
- **Agent 是装修工**——自己决定要用哪些工具、哪些技能、什么顺序

**关键认知**：Skill 不是 Tool 的替代，而是 Tool 的**上层封装**。一个 Skill 内部可以调多个 Tool，甚至调 MCP 工具。

---

## 3. 为什么需要 Skill

13 篇的 ReAct Agent 已经能处理多步任务。但它有个根本问题：**每次结果可能不一样**。

用户说"帮我退掉订单88024"：

```
ReAct 版本可能的执行路径：
  路径 A：查订单 → 未发货 → 取消 → 通知用户（3 步）
  路径 B：查订单 → 未发货 → 直接取消，忘了通知（2 步）
  路径 C：查订单 → 未发货 → 先问用户确认再取消（4 步）
```

同样的输入，每次行为不一致——**这在生产环境是灾难**：

| 场景 | 为什么 Skill 更合适 |
|------|---------------------|
| 退款、审批、工单 | 有合规要求，步骤必须固定 |
| 高频重复任务 | 每次让 LLM 推理浪费 token 和延迟 |
| 多步有副作用 | 中间步骤失败要回滚，流程必须可控 |
| 需要审计 | 固定流程才能记录"第几步做了什么" |

**Skill 的核心价值**：把"怎么做"从 LLM 的临场决策，变成开发者的**显式编码**。LLM 只负责"要不要做"和"传什么参数"。

## 4. 设计 Skill 基类

新建 `app/skills/base.py`：

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class SkillResult:
    success: bool
    message: str

class Skill(ABC):
    """
    Skill 基类：固定流程的封装单元。
    子类必须定义 name / description / parameters，并实现 run()。
    """
    name: str = ""
    description: str = ""
    parameters: dict = {}

    @abstractmethod
    async def run(self, **kwargs) -> SkillResult:
        """执行技能的内部流程。"""
        ...
```

设计要点：

| 属性 | 作用 |
|------|------|
| `name` | 技能名，LLM 用它触发（如 `process_refund`） |
| `description` | 告诉 LLM 什么情况下用这个技能（第 12 篇讲的原则） |
| `parameters` | JSON Schema，和 Tool 的 parameters 格式一样 |
| `run()` | 内部固定流程，异步，可以调任意工具 |

## 5. 实现第一个 Skill：处理退货

新建 `app/skills/refund_skill.py`：

```python
import logging

from app.skills.base import Skill, SkillResult

logger = logging.getLogger(__name__)

class RefundSkill(Skill):
    name = "process_refund"
    description = (
        "处理退货退款。当用户明确表示要退货、退款、取消订单时使用。"
        "需要订单号，退货原因可选。"
    )
    parameters = {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "订单号，如 88024"},
            "reason": {"type": "string", "description": "退货原因，可选"},
        },
        "required": ["order_id"],
    }

    async def run(self, order_id: str, reason: str = "") -> SkillResult:
        # 延迟导入，避免循环依赖：
        # refund_skill → agent_service → registry → refund_skill（加载中）
        from app.services.agent_service import TOOL_IMPL

        # 第 1 步：查订单状态（固定）
        try:
            status = TOOL_IMPL["get_order_status"](order_id=order_id)
        except Exception as e:
            logger.exception("查订单失败")
            return SkillResult(success=False, message=f"查订单失败: {e}")

        # 第 2 步：判断能否取消（固定规则，不依赖 LLM）
        if "已发货" in status:
            return SkillResult(
                success=False,
                message=f"订单 {order_id} 已发货，无法直接取消。请走退货流程：签收后 7 天内申请退货。",
            )

        # 第 3 步：取消订单（固定）
        try:
            cancel_result = TOOL_IMPL["cancel_order"](order_id=order_id)
        except Exception as e:
            logger.exception("取消订单失败")
            return SkillResult(success=False, message=f"取消订单失败: {e}")

        # 第 4 步：通知用户（固定）
        # 生产环境这里会调 send_sms / send_email 工具
        notify_note = f"已通知用户订单 {order_id} 取消成功。"

        return SkillResult(
            success=True,
            message=(
                f"订单 {order_id} 已成功取消。"
                f"原因：{reason or '未说明'}。"
                f"退款将在 3 个工作日内原路退回。{notify_note}"
            ),
        )
```

### 5.1 关键设计点

| 点 | 说明 |
|----|------|
| 步骤写死在 `run()` 里 | 不管 LLM 怎么想，第 1 步一定是查订单，第 2 步一定是判断规则 |
| 规则用 Python if/else | "已发货不能取消"这种业务规则，代码判断比 LLM 判断可靠 |
| 失败返回 SkillResult | 不抛异常，让上层决定怎么告诉 LLM |
| 复用 TOOL_IMPL | Skill 内部直接用 13 篇的工具实现，不用重复造轮子 |

对比 13 篇的 ReAct：同样一句话，ReAct 版让 LLM 每步决策；Skill 版内部固定流程，LLM 只看到"调用了 process_refund，返回了成功/失败"。

## 6. Skill 注册与调度

新建 `app/skills/registry.py`：

```python
import logging

from app.skills.base import Skill

logger = logging.getLogger(__name__)

_registry: dict[str, Skill] = {}

def register(skill: Skill) -> None:
    """注册一个 Skill。应用启动时调用。"""
    if not skill.name:
        raise ValueError("Skill 必须有 name")
    _registry[skill.name] = skill
    logger.info("Skill registered: %s", skill.name)

def list_skills() -> list[Skill]:
    return list(_registry.values())

def list_skill_schemas() -> list[dict]:
    """把 Skill 转成 OpenAI tools schema，让 LLM 决定用不用。"""
    return [
        {
            "type": "function",
            "function": {
                "name": s.name,
                "description": s.description,
                "parameters": s.parameters,
            },
        }
        for s in _registry.values()
    ]

async def dispatch(name: str, args: dict) -> str:
    """执行一个 Skill，返回文本结果（喂回 LLM）。"""
    skill = _registry.get(name)
    if not skill:
        return f"未知技能: {name}"
    try:
        result = await skill.run(**args)
        return result.message
    except TypeError as e:
        # 参数不匹配（比如 LLM 漏了必填参数）
        return f"技能参数错误: {e}"
    except Exception as e:
        logger.exception("Skill %s failed", name)
        return f"技能执行失败: {e}"
```

### 6.1 启动时注册 Skill

在 `main.py` 或 `app/__init__.py` 里加：

```python
from app.skills.registry import register
from app.skills.refund_skill import RefundSkill

register(RefundSkill())
```

以后新增 Skill 只需要：

```python
register(CancelOrderSkill())
register(ChangeAddressSkill())
register(ResendInvoiceSkill())
```

## 7. 接入 Agent：Skill 和 Tool 一起给 LLM

Skill 和 Tool 在 LLM 眼里看起来一样——都是一份 schema。所以在 `agent_service.py` 里加一个函数（和前面的 `agent_chat`、`agent_chat_mcp` 同文件），合并两者：

```python
import json
import logging

from app.skills.registry import list_skill_schemas, dispatch as dispatch_skill

# 注意：这个函数就在 agent_service.py 内部，
# TOOLS / TOOL_IMPL / MAX_ITERATIONS / SYSTEM_PROMPT_MCP 都是本文件已有的变量，直接用，不要再 import 自己。

logger = logging.getLogger(__name__)

async def agent_chat_with_skills(
    question: str,
    session_id: str | None = None,
) -> str:
    # 1. 合并 Tool + Skill 的 schema
    all_tools = TOOLS + list_skill_schemas()

    # 2. 拼 messages
    history = []
    if session_id:
        history = await summarize_old_history(session_id, keep_recent=6)
    messages = build_messages(SYSTEM_PROMPT_MCP, history, question)

    # 3. ReAct 循环
    for _ in range(MAX_ITERATIONS):
        resp = await client.chat.completions.create(
            model=settings.ollama_model,
            messages=messages,
            tools=all_tools,
            temperature=0.0,
        )
        msg = resp.choices[0].message

        if not msg.tool_calls:
            answer = msg.content or ""
            if session_id:
                add_message(session_id, "user", question)
                add_message(session_id, "assistant", answer)
            return answer

        messages.append(msg.model_dump(exclude_none=True))
        for tool_call in msg.tool_calls:
            func_name = tool_call.function.name
            try:
                args = json.loads(tool_call.function.arguments)
            except json.JSONDecodeError:
                args = {}

            # 4. 关键：判断是 Skill 还是 Tool
            if func_name in _skill_names():
                result = await dispatch_skill(func_name, args)
            elif func_name in TOOL_IMPL:
                try:
                    result = TOOL_IMPL[func_name](**args)
                except Exception as e:
                    result = f"工具执行失败: {e}"
            else:
                result = f"未知工具/技能: {func_name}"

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": result,
            })

    return "抱歉，任务太复杂，我暂时处理不了。"

def _skill_names() -> set[str]:
    from app.skills.registry import list_skills
    return {s.name for s in list_skills()}
```

**关键设计**：给 LLM 的 `tools` 参数里，Skill 和 Tool 混在一起。LLM 不知道哪个是 Tool、哪个是 Skill——它只知道有一份份 schema。执行时分流。

## 8. FastAPI 接口

`app/routers/agent.py` 加：

```python
@router.post("/chat-skill")
async def chat_skill(req: AgentRequest):
    if not req.question.strip():
        raise HTTPException(status_code=422, detail="question 不能为空")
    answer = await agent_chat_with_skills(req.question, req.session_id)
    return {"answer": answer, "session_id": req.session_id}
```

## 9. 验证

### 9.1 正常退款

```json
POST /api/agent/chat-skill
{"question": "帮我退掉订单88024，买错了", "session_id": "u001"}
```

预期：
1. LLM 识别为 `process_refund` Skill，传入 `order_id=88024, reason=买错了`
2. Skill 内部：查订单 → 未发货 → 取消 → 通知
3. 返回："订单 88024 已成功取消。原因：买错了。退款将在 3 个工作日内原路退回。"

### 9.2 边界情况：订单已发货

```json
{"question": "帮我退掉订单88023", "session_id": "u002"}
```

预期：
1. LLM 识别为 `process_refund`，传入 `order_id=88023`
2. Skill 内部：查订单 → 已发货 → 拒绝取消
3. 返回："订单 88023 已发货，无法直接取消。请走退货流程：签收后 7 天内申请退货。"

**关键**：无论 LLM 怎么想，这个判断一定在代码里做，不是让 LLM 自由发挥。

### 9.3 对比 ReAct 版本

同样的输入，ReAct 版本可能：
- 有时调 `get_order_status` 后忘了取消
- 有时直接把"已发货"的订单也取消掉（因为它可能不遵守业务规则）
- 有时先问用户确认

Skill 版本的行为完全一致——这就是它的价值。

## 10. 什么时候用 Skill，什么时候用 ReAct

| 场景 | 用什么 | 原因 |
|------|--------|------|
| 流程固定、高频重复 | Skill | 稳定、可测、省 token |
| 有合规要求（退款、审批） | Skill | 步骤必须固定，不能靠 LLM 临场判断 |
| 需要审计日志 | Skill | 固定步骤才能记录"第几步做了什么" |
| 任务多变、需要规划 | ReAct | LLM 自主决策更灵活 |
| 探索性任务（如"帮我分析下这段文本"） | ReAct | 没有固定流程 |

**混合模式（生产常见）**：Agent 先用 ReAct 规划，发现可以走 Skill 就直接 dispatch Skill。Skill 内部再调工具或 MCP 工具。三层配合。

## 11. Skill 的进阶设计

### 11.1 Skill 内部可以调 MCP 工具

14 篇的 MCP 工具和 15 篇的 Skill 不冲突。Skill 的 `run()` 里调 MCP Client 即可：

```python
from app.core.mcp_client import call_mcp_tool

class RefundSkill(Skill):
    async def run(self, order_id: str, reason: str = "") -> SkillResult:
        status = await call_mcp_tool(MCP_SERVER, "get_order_status", {"order_id": order_id})
        ...
```

分工：
- MCP 解决"工具从哪来"（跨进程、跨语言）
- Skill 解决"流程怎么沉淀"（固定步骤封装）

### 11.2 Skill 可以复用其他 Skill

复杂 Skill 内部可以调其他 Skill，形成能力树：

```python
class VipRefundSkill(Skill):
    async def run(self, order_id: str):
        # 先走普通退款
        result = await dispatch("process_refund", {"order_id": order_id, "reason": "VIP 优先"})
        # 再补一个 VIP 专属动作
        await dispatch("vip_compensate", {"order_id": order_id})
        return SkillResult(success=True, message=f"VIP 退款完成：{result}")
```

### 11.3 Skill 支持参数校验

Skill.parameters 里可以加更严格的约束：

```python
"parameters": {
    "type": "object",
    "properties": {
        "order_id": {
            "type": "string",
            "pattern": "^\\d{5}$",   # 5 位数字
            "description": "订单号，5 位数字",
        },
    },
    "required": ["order_id"],
}
```

LLM 输出参数后，`run()` 里第一件事就是 `jsonschema.validate(args, self.parameters)`，不合法直接返回错误，不进业务逻辑。

## 13. 失败模式速查表

| 现象 | 原因 | 解法 |
|------|------|------|
| LLM 不调 Skill，直接调底层工具 | Skill 的 description 不够明确 | 写清"什么场景用 Skill"；system prompt 引导"优先用 Skill" |
| Skill 参数错（漏传 order_id） | LLM 没提取到参数 | 参数加 description；必要时 Skill 内部先问用户补参数 |
| Skill 内部工具挂了没兜底 | `run()` 里没 try/except | 每个工具调用包 try；返回 `SkillResult(success=False)` |
| Skill 步骤太多，LLM 等不及 | 内部串行调用慢 | 能用并行的并行（`asyncio.gather`）；耗时步骤异步化 |
| Skill 复用其他 Skill 循环调用 | A 调 B，B 又调 A | 加调用栈深度限制（如最多 3 层） |
| 加新 Skill 忘了 register | main.py 里没注册 | 检查启动日志是否有 `Skill registered: xxx` |
| Skill 内部报错但 LLM 看不到 | dispatch 里没兜异常 | dispatch 统一 try/except，把错误转字符串喂回 LLM |
