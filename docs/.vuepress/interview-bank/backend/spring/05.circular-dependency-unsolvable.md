## 题目

Spring 中哪些场景的循环依赖是无法解决的？

## 答案

Spring **不能**靠三级缓存解决的典型场景：

1. **构造器注入**形成的循环依赖（创建时就必须拿到完整依赖，无法先暴露半成品）。
2. **prototype** 作用域的循环依赖（每次新建，没有单例池提前曝光机制）。
3. **@Async / 某些工厂方法**等导致需要「已完成代理/初始化」才能注入，时机对不上时也可能失败。
4. 设计层面：多级复杂环 + 依赖「初始化已完成」的逻辑，即使勉强启动也可能行为怪异——应重构。

### 解释与扩展

#### 1. 构造器循环

```text
A(B b) ←→ B(A a)
```

创建 A 必须先有 B，创建 B 必须先有 A → 死锁式失败，抛 `BeanCurrentlyInCreationException`。

解法：改构造器一侧为 Setter/字段、引入第三方模块解环、或 `@Lazy` 推迟一侧解析。

#### 2. Prototype 循环

原型不进单例三级缓存那套「提前曝光」；互相依赖会反复创建或直接失败。

#### 3. 和「能解决」的分界线

| 场景 | 能否解决 |
|---|---|
| 单例 + Setter/字段环 | 通常能（三级缓存） |
| 单例 + 构造器环 | 不能（或靠 `@Lazy` 绕） |
| Prototype 环 | 不能 |
| 单例与 Prototype 混用环 | 视注入方式，常踩坑 |

#### 4. 工程建议

循环依赖往往是 **模块边界不清** 的信号：抽接口/事件/应用服务，比打开 `spring.main.allow-circular-references` 更健康。

### 注意

- `@Lazy` 本质是注入代理推迟初始化，是绕过不是「三级缓存支持构造器环」。
- Boot 2.6+ 默认不允许循环依赖，面试要提这一点。
