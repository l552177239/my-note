## 题目

IoC / DI 核心原理，主要解决什么问题？

## 答案

1. **IoC（控制反转）**：对象创建与依赖装配的控制权从业务代码交给容器；你不再 `new` 依赖，由容器按配置创建并注入。
2. **DI（依赖注入）**：IoC 的落地方式——构造器 / Setter / 字段注入，把依赖「推」给对象。
3. **主要解决**：硬编码耦合、难测、难替换实现；统一生命周期与配置，便于 AOP、事务等横切能力挂接。

### 解释与扩展

#### 1. 没有 IoC 时的问题

```java
// 业务自己 new → 强耦合具体实现，换 Mock / 换实现要改代码
class OrderService {
  private PaymentClient client = new AlipayClient();
}
```

痛点：依赖方向写死、单元测试难、横切逻辑（事务/日志）只能侵入业务。

#### 2. IoC + DI 后

```text
  业务类只声明「我需要什么」
       ↓
  容器负责：实例化 → 解析依赖 → 注入 → 初始化 → 托管生命周期
```

口述要点：
- **IoC** 是思想（谁控制谁）；**DI** 是手段（怎么把依赖塞进去）。
- Spring 里 `BeanFactory` / `ApplicationContext` 就是 IoC 容器。
- 推荐 **构造器注入**：依赖不可变、必填清晰、利于测试。

#### 3. 和「工厂模式」的关系

工厂也能解耦创建，但通常要手写工厂；Spring 用 **反射 + 元数据（注解/XML）** 做通用工厂，并叠加作用域、AOP、事件等。

### 注意

- 面试别只背「反转」：要说清 **反转的是依赖对象的创建与装配权**。
- DI ≠ 必须 `@Autowired`；构造器注入同样是 DI。
- IoC 是后续 Bean 生命周期、循环依赖、AOP、事务代理的地基。
