## 题目

CPU 密集 / IO 密集如何设置线程池？

## 答案

1. **先分清任务类型**：CPU 密集（算力打满）vs IO 密集（大量等待磁盘 / 网络 / DB）；**不要混在一个池里硬估**。
2. **CPU 密集**：线程数 ≈ **CPU 核数 `N`**，或 **`N + 1`**（多一个兜切换 / 偶发阻塞）；再多只会抢核、上下文切换变重。
3. **IO 密集**：线程数可以 **大于 `N`**，经验式：**`N * (1 + WT/ST)`**（等待时间 / 计算时间），或粗估 **`2N`～`N*几倍`**；本质是用更多线程填满「等 IO」的空隙。
4. **落地**：用 `availableProcessors()` 取 `N`，再压测调 core / max / 队列；生产手写有界 `ThreadPoolExecutor`，业务池隔离。

### 解释与扩展

#### 1. 两类任务差在哪

| 类型 | 特征 | 瓶颈 | 多开线程的效果 |
|---|---|---|---|
| **CPU 密集** | 纯算、编解码、压缩、复杂业务计算 | CPU | 线程 ≫ `N` → 争用 CPU，切换开销升，吞吐反而掉 |
| **IO 密集** | HTTP、DB、Redis、文件、RPC | 等待外设 | 一线程阻塞时别的还能跑；适度多开可提高吞吐 |

`N = Runtime.getRuntime().availableProcessors()`（容器里可能还要看 CPU quota，别盲信宿主机核数）。

#### 2. 经验公式（面试够用）

**CPU 密集**

```text
线程数 ≈ N          // 或 N + 1
core ≈ max ≈ N（或 N+1）
```

理由：真正在算的线程最多也就 `N` 个能并行；多出来的大多在排队等 CPU。

**IO 密集**

```text
线程数 ≈ N * (1 + WT / ST)
```

- `WT`：等待 IO 的时间  
- `ST`：真正占用 CPU 的时间  

例：`N=8`，等待约占算的 9 倍（`WT/ST=9`）→ 约 `8 * 10 = 80`。  
说不清比例时，口述可用 **`2N` 起跳，压测往上探**，并盯延迟与拒绝率。

```java
int n = Runtime.getRuntime().availableProcessors();
// CPU 密集示例
new ThreadPoolExecutor(n, n, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(200), ..., AbortPolicy);

// IO 密集示例（数字需压测，这里仅示意）
int ioSize = n * 4;
new ThreadPoolExecutor(ioSize, ioSize, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000), ..., CallerRunsPolicy);
```

#### 3. 不只改「线程数」

池子还要一起想清：
- **有界队列**：避免 `Executors` 无界队列 OOM。
- **拒绝策略**：打满时抛 / 调用者跑 / 丢——按能否降级选。
- **池隔离**：CPU 重任务、IO 调用、定时任务分池，避免算力任务堵死 IO 池或反过来占满 Tomcat 线程。
- **混合任务**：能拆就拆（算完再丢 IO 池）；拆不开就偏 IO 估，并限流，别按纯 CPU 设太小。

#### 4. 和「越多越好」的边界

- 线程过多：栈内存、调度、锁争用、连接池打满（DB 连接往往比线程更紧）。
- 线程过少：CPU 空转等 IO，吞吐上不去。
- **公式给初值，压测给终值**：看 CPU%、RT、队列长度、拒绝次数、下游连接池。

Java 21+ **虚拟线程**：IO 密集可大量阻塞式写法，线程数心智不同；传统平台线程池题仍按上面答，调度细节见「虚拟线程与平台线程」题。

### 注意

- 高频坑：IO 任务也按 `N` 设 → 核闲着、吞吐低；CPU 任务按几十上百 → 切换爆炸。
- `newCachedThreadPool` 不是「IO 自动最优」，是线程可无限涨，高峰易打爆。
- 容器 / K8s：`availableProcessors` 可能已反映 limit，仍要以实际 quota 与压测为准。
- 与上一题（核心参数 / 执行流程 / 拒绝策略）衔接：先懂参数与流程，再按 CPU/IO 估线程数；与 ThreadLocal 题衔接：池复用长线程务必 `remove`。
