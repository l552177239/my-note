## 题目

synchronized vs ReentrantLock 如何选？

## 答案

1. **共同点**：都可重入、互斥；都能提供临界区内的 **原子性 + 可见性 + 有序性**（解锁 HB 随后加锁）。
2. **默认优先 `synchronized`**：语法简单、自动释放、JVM 持续优化（偏向 / 轻量 / 重量）；日常互斥够用就够。
3. **需要高级能力再用 `ReentrantLock`**：可中断获取、限时 / 尝试 `tryLock`、公平锁、多个 `Condition` 等待队列。
4. **选型口诀**：简单互斥 → `synchronized`；要「试锁 / 打断 / 公平 / 多条件」→ `ReentrantLock`（务必 `finally` 里 `unlock`）。

### 解释与扩展

#### 1. 对照表

| 维度 | synchronized | ReentrantLock |
|---|---|---|
| 类型 | JVM 关键字 / 监视器 | `java.util.concurrent.locks` API |
| 释放 | 出代码块自动释放 | 必须手写 `unlock()`（通常放 `finally`） |
| 可中断等待 | 抢锁阶段不可响应中断 | `lockInterruptibly()` 可中断 |
| 尝试 / 限时 | 无 | `tryLock()` / `tryLock(time, unit)` |
| 公平性 | 非公平（由 JVM 调度） | 构造可指定公平 / 非公平（默认非公平） |
| 条件队列 | 一把锁一个 wait 集（`wait`/`notify`） | `newCondition()` 可多个条件队列 |
| 可重入 | ✓ | ✓（可查 `getHoldCount()`） |
| 性能直觉 | 无争用极轻；有争用靠 JVM 锁升级 | 与 `synchronized` 同量级；优势在**功能**而非「一定更快」 |

#### 2. 用法形态

```java
// synchronized：作用域即锁范围，异常也会释放
synchronized (lock) {
  // 临界区
}

// ReentrantLock：显式加解锁，漏 unlock 会死锁
lock.lock();
try {
  // 临界区
} finally {
  lock.unlock();
}
```

需要「拿不到就干别的 / 超时放弃」：

```java
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
  try {
    // ...
  } finally {
    lock.unlock();
  }
} else {
  // 降级、跳过、入队稍后重试
}
```

多条件（生产者 / 消费者拆开通知）：

```java
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();
// put 满了 await notFull；take 空了 await notEmpty；对应 signal
```

`synchronized` 只有一个 wait 集，唤醒常靠 `notifyAll` + 再判断条件，不如多 `Condition` 精确。

#### 3. 如何选（面试口述）

| 场景 | 选谁 | 原因 |
|---|---|---|
| 普通临界区、方法级互斥 | **synchronized** | 简单、不易忘释放、JVM 优化成熟 |
| 拿不到锁要立刻返回 / 超时 | **ReentrantLock** | 只有 `tryLock` |
| 等待锁时要响应中断（可取消任务） | **ReentrantLock** | `lockInterruptibly` |
| 强公平、避免饥饿 | **ReentrantLock(true)** | synchronized 无法声明公平 |
| 多种等待条件分开唤醒 | **ReentrantLock + Condition** | 比单一 `wait`/`notify` 清晰 |
| 只是「听说 ReentrantLock 更快」 | **别换** | 现代 HotSpot 下无功能需求时优先 synchronized |

口述收束：两者语义上都是互斥锁；**差别在可控能力与写法成本**，不是「一个过时一个先进」。

### 注意

- `ReentrantLock` 最大坑：异常路径忘 `unlock` → 永久占锁；`synchronized` 没有这个问题。
- 公平锁吞吐通常更差，只在明确要防饥饿时开；默认非公平与 `synchronized` 更接近。
- 读多写少优先考虑 `ReadWriteLock` / `StampedLock` 或无锁结构，不必死磕这两把互斥锁谁更快。
- 与上一题（`synchronized` 实现 / 锁升级）衔接：理解监视器优化后，更清楚「无额外功能时不必换 ReentrantLock」。
- 与 JMM / `volatile` 题衔接：需要互斥临界区用锁；只保证标志可见用 `volatile` 即可。
