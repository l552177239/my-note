## 题目

CompletableFuture 的使用场景，异常处理机制？

## 答案

1. **是什么**：实现 `CompletionStage` + `Future` 的 **可组合异步编排**：任务完成后再 `thenXxx` 接力，支持并行汇合、超时、手动完成。
2. **典型场景**：服务间 **扇出 / 扇入**（多 RPC 并行再合并）、流水线（查库→算→写缓存）、与回调/网关异步对接；替代手写一堆 `Future.get` 嵌套。
3. **异常机制**：阶段失败后进入 **异常完成**；后续可用 `exceptionally` / `handle` / `whenComplete` / `exceptionallyCompose` 恢复或观测；`get`/`join` 时常见包装成 `ExecutionException` / `CompletionException`。
4. **注意**：默认线程常是 **`ForkJoinPool.commonPool()`**（`*Async` 无 Executor 时）；回调里别长时间阻塞；异常要在链上显式处理，否则 `join` 才炸。

### 解释与扩展

#### 1. 使用场景

| 场景 | 常用 API | 直觉 |
|---|---|---|
| 异步执行 | `supplyAsync` / `runAsync` | 提交到池，返回 CF |
| 串行接力 | `thenApply` / `thenCompose` | 有返回值变换；扁平嵌套 CF 用 Compose |
| 消费结果 | `thenAccept` / `thenRun` | 只要副作用 |
| 两路合并 | `thenCombine` / `thenAcceptBoth` | A、B 都成功再合 |
| 多路等待 | `allOf` / `anyOf` | 全完成 / 任一完成 |
| 手动完成 | `complete` / `completeExceptionally` | 对接回调、监听器 |
| 超时 | `orTimeout` / `completeOnTimeout`（Java 9+） | 防止一直挂 |

扇出扇入口述：

```text
        ┌─ supplyAsync(RPC1) ─┐
请求 ───┼─ supplyAsync(RPC2) ─┼─ thenCombine / allOf → 聚合 → 返回
        └─ supplyAsync(RPC3) ─┘
```

```java
CompletableFuture<User> u = supplyAsync(() -> userClient.get(id), ioPool);
CompletableFuture<Order> o = supplyAsync(() -> orderClient.list(id), ioPool);

CompletableFuture<VO> vo = u.thenCombine(o, (user, orders) -> toVO(user, orders));
// 或
CompletableFuture.allOf(u, o).thenApply(v -> toVO(u.join(), o.join()));
```

`thenApply` vs `thenCompose`：
- `thenApply`：`T -> U`（普通值）。
- `thenCompose`：`T -> CompletionStage<U>`（避免 `CF<CF<U>>`）。

和线程池 / 虚线程题衔接：IO 扇出可把 Executor 换成虚线程 per-task；CPU 段用有界平台池。

#### 2. 异常处理机制

**完成状态**：每个阶段要么 **正常完成**（有结果），要么 **异常完成**（带着 Throwable）。上游异常默认会 **沿链传递**，中间纯 `thenApply` 不会执行，直到碰到能处理异常的阶段或终端 `get`/`join`。

| API | 行为 | 何时用 |
|---|---|---|
| **`exceptionally`** | `(Throwable) -> T`，失败时给出 **兜底结果**，变成正常完成 | 降级、默认值 |
| **`exceptionallyCompose`** | 失败时返回另一个 `CompletionStage` | 失败后改走异步补偿 |
| **`handle`** | `(T, Throwable) -> U`，成功失败都进 | 统一映射结果/错误码 |
| **`whenComplete`** | `(T, Throwable) -> void`，**不改变**结果（除非回调自己再抛） | 打日志、监控 |
| **`completeExceptionally`** | 主动把 CF 标失败 | 回调里失败、超时取消语义 |

包装差异（面试常问）：

| 取出方式 | 失败时常见异常 |
|---|---|
| `future.get()` | `ExecutionException`（`getCause` 才是业务异常）；中断 → `InterruptedException` |
| `future.join()` | `CompletionException` 包装；不声明受检异常，更适合链式 |
| 链内回调 | 原始异常进 `exceptionally`/`handle` 的参数；再往外传时常再包一层 |

```java
supplyAsync(() -> { throw new IllegalStateException("boom"); }, pool)
  .exceptionally(ex -> {
    // ex 可能是 CompletionException，必要时解开 getCause()
    log.warn("failed", ex);
    return fallback();
  })
  .thenAccept(this::ok);

// 统一处理
supplyAsync(this::load, pool)
  .handle((v, ex) -> ex == null ? v : fallback())
  .whenComplete((v, ex) -> metrics.record(ex == null));
```

`allOf` 与异常：`allOf` 本身结果是 `Void`；任一失败时，`allOf(...).join()` 会以 `CompletionException` 失败；要拿各个结果仍需对子 CF `join`，并各自或统一 `handle`。

#### 3. 线程与常见坑

- `supplyAsync(supplier)` 无 Executor → **`ForkJoinPool.commonPool()`**（并行度 ≈ CPU-1）；跟业务 IO 池混用要显式传 **自己的 Executor**。
- `thenApply` 默认在 **完成该阶段的同一线程** 继续（可能是提交线程或池线程）；要切池用 `thenApplyAsync(..., executor)`。
- 回调里 **阻塞**（同步 RPC、`Thread.sleep`）会占住 commonPool / 业务池，拖垮其他 CF。
- 异常若只 `whenComplete` 打日志却不 `exceptionally`/`handle`，调用方 `join` 仍会炸——**观测 ≠ 恢复**。

### 注意

- `CompletableFuture` 解决的是 **编排与组合**，不是替代限流；扇出仍要护住下游（信号量、连接池）。
- 取消：`cancel` 对未完成阶段标异常完成，**不保证**中断正在跑的任务线程；需合作式取消或自己响应中断。
- 与裸 `Future` 比：多了非阻塞链式组合；与响应式框架比：JDK 内置、模型更轻，背压等能力弱。
- 面试加分：能举扇出扇入例子，并分清 `exceptionally` / `handle` / `whenComplete`，以及 `get` vs `join` 的异常包装。
