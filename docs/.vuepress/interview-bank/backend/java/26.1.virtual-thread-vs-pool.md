## 题目

虚拟线程与线程池如何取舍？哪些场景不适合？

## 答案

1. **取舍原则**：任务是 **大量阻塞等待**（网络 / DB / 文件）→ 优先 **虚拟线程（一任务一虚线程）**；任务是 **吃 CPU** 或必须 **严格限并行** → 继续用 **有界平台线程池**（或虚线程 + 信号量限流）。
2. **虚线程侧写法**：少用「大池复用工人」，多用 `Executors.newVirtualThreadPerTaskExecutor()` / `Thread.ofVirtual()`；下游容量用 **信号量、连接池、隔板** 限制，而不是靠把线程数调很小。
3. **不适合虚线程（或收益差）**：CPU 密集、极短非阻塞任务、依赖线程身份的池化资源、大量 `synchronized`+阻塞（pinning）、与「固定少量平台线程」强绑定的库。
4. **共存**：不是二选一——IO 扇出用虚线程，算力段丢到有界平台池 / `parallelStream` 受控并行。

### 解释与扩展

#### 1. 怎么选（决策表）

| 场景特征 | 更合适 | 原因 |
|---|---|---|
| 高并发阻塞 IO、每请求多次 RPC/DB | **虚线程** | 阻塞可卸载 carrier，用同步代码拿异步吞吐 |
| 纯计算、编解码、压缩、复杂算法 | **平台线程池（≈核数）** | 虚线程不增加算力，过多只会争 carrier / CPU |
| 必须保护下游（DB 最大连接 50） | 虚线程 **+ 信号量/连接池**，或平台池 max≈下游 | 限的是资源，不是「线程贵不贵」 |
| 任务极短、几乎不阻塞 | 平台池或直接调用 | 虚线程调度开销可能盖过收益 |
| 旧代码大量线程池调参已稳定 | 可保持；热点 IO 路径再迁虚线程 | 渐进替换，不必全站一刀切 |

口述口诀：
- **线程池**：贵的是「平台工人」，所以要复用、排队、拒绝。
- **虚线程**：工人很便宜，贵的是 **下游与共享资源**，所以要限流、隔离，而不是先想 core/max。

#### 2. 推荐用法对比

```java
// 平台线程池：有界工人 + 有界队列 + 拒绝策略
new ThreadPoolExecutor(n, n, ..., new ArrayBlockingQueue<>(q), ..., handler);

// 虚线程：一任务一线程（Executor 只是提交入口，不是「复用虚线程池」心智）
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
  exec.submit(() -> blockingIo());
}

// 虚线程也要限并行时：信号量（例：最多 100 个并发打 DB）
Semaphore permits = new Semaphore(100);
permits.acquire();
try { dbCall(); } finally { permits.release(); }
```

| | 传统平台池 | 虚线程 per-task |
|---|---|---|
| 主要旋钮 | core / max / 队列 / 拒绝 | 有界并发（信号量等）+ 下游池 |
| 任务排队 | 常在 workQueue | 可在调用方 / 信号量等待 / 业务队列 |
| 拒绝 | Abort / CallerRuns… | 自己做限流与降级 |
| 适合扩展 | 控住平台线程数 | 控住 **扇出** 与 **资源** |

#### 3. 哪些场景不适合（重点）

1. **CPU 密集**  
   虚线程不能让 8 核变成 800 核；百万虚线程抢 carrier，上下文更乱。应用有界平台池，`≈ N` 或 `N+1`。

2. **频繁 pinning**  
   在 `synchronized` 里做阻塞 IO、或大量未适配本地阻塞：carrier 被钉住，吞吐崩回「昂贵平台线程」。长临界区改 `ReentrantLock`，或别在钉住路径上睡。

3. **把虚线程再塞进「固定大小平台池」当工人**  
   例如自定义池只用平台线程跑虚线程任务、或层层嵌套池化，失去 M:N 优势，还难排查。

4. **依赖「线程少、可缓存」的线程绑定**  
   大对象 `ThreadLocal`、按线程缓存的连接/缓冲区：虚线程数量爆炸 → 内存与泄漏风险放大；改参数传递 / Scoped Value（Java 21+）等。

5. **与「当前必须是平台线程」的假设死绑的库**  
   少数 JNI、旧监控、错误地用线程 ID 做强亲和的组件；需验证后再上。

6. **需要严格 FIFO / 单一线程演员模型**  
   单线程 `Executor` 或 actor 保证顺序时，虚线程「海量并发」不是目标；继续单线程或有序队列。

7. **延迟极端敏感且任务极短**  
   调度与分配开销可能不如直接在当前线程做完；先测再换。

#### 4. 和线程池题怎么串

- 先问调度：见「虚拟线程与平台线程」——M:N、mount/unmount。  
- 再问参数：平台池仍要 core→队列→max→拒绝。  
- 本题收束：**IO 扇出 → 虚线程；算力与硬限流 → 平台池 / 信号量；混合则分段。**

### 注意

- 「不适合」不等于「不能跑」：多数是 **收益差或易踩坑**，要以压测（吞吐、RT、CPU、下游拒绝、pinning 监控）为准。
- 虚线程降低的是 **等待成本**，不替代 **限流、超时、舱壁、连接池**。
- 面试加分：能说「一任务一虚线程 + 信号量护下游」，并列出 CPU 密集、`synchronized` pinning、ThreadLocal 放大三条不适用。
