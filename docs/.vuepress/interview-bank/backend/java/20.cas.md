## 题目

CAS 原理？ABA、忙等、高竞争如何处理？★

## 答案

1. **CAS（Compare-And-Swap）**：原子地「读当前值 → 与期望值比较 → 相等则换成新值」；硬件 / CPU 原语（如 `cmpxchg`），Java 里经 `Unsafe` / `VarHandle` 暴露给 `Atomic*`。
2. **成功语义**：期望值 == 内存值 → 写入新值并返回 true；否则失败、不改内存，调用方通常 **重读再试**（乐观锁）。
3. **ABA**：值从 A→B→A，CAS 仍成功，但中间状态可能已破坏不变量；用 **版本号 / 戳**（`AtomicStampedReference`）或避免「值相等即安全」的假设。
4. **忙等**：失败即自旋重试，占 CPU、不让出；适合临界区极短、竞争轻。
5. **高竞争**：换 **分段 / 打散热点**（`LongAdder`）、有界自旋后退、或退回 **锁**；别在长逻辑上死磕 CAS 循环。

### 解释与扩展

#### 1. CAS 原理

伪代码（单变量）：

```text
boolean cas(addr, expected, newVal):
  // 整段对其他核原子可见，不可插入
  if *addr == expected:
    *addr = newVal
    return true
  return false
```

Java 侧典型用法：

```java
AtomicInteger n = new AtomicInteger(0);
// 等价于「无锁自增」的核心循环
int prev, next;
do {
  prev = n.get();
  next = prev + 1;
} while (!n.compareAndSet(prev, next));
```

要点：
- **乐观**：先假定无冲突，冲突再重试；对比悲观锁「先占坑再干活」。
- **无锁 ≠ 无线程安全开销**：失败路径可能多次 CAS；成功路径无阻塞、无上下文切换。
- **可见性**：`Atomic*` 字段语义类似 `volatile`；一次成功的 CAS 对后续读建立可见顺序（可口述为带原子更新的 volatile 写）。
- **只能保证「这一次比较并交换」原子**；业务上多字段一致性仍要设计（或上锁）。

和锁对比（面试口述）：

| | CAS / 原子类 | synchronized / Lock |
|---|---|---|
| 互斥方式 | 乐观，失败重试 | 悲观，拿不到就等 |
| 适合 | 冲突少、操作极短 | 冲突多、临界区较长 / 要等条件 |
| 失败表现 | 烧 CPU 自旋 | 可能阻塞、上下文切换 |
| ABA | 要额外处理 | 锁住临界区通常无此问题 |

#### 2. ABA 问题

场景：栈顶指针 / 池化对象引用被 CAS 更新时，**值回到旧值 ≠ 状态没变过**。

```text
线程1：读到 top = A，准备 cas(A → C)
线程2：pop A，push B，再 push A（top 又是 A）
线程1：cas(A → C) 成功 —— 但中间栈结构 / 对象内容可能已不同
```

危害：链表 / 栈 / 「对象复用 + 引用相等」场景下，可能链错节点或忽略中间释放。

处理：
| 手段 | 思路 | Java |
|---|---|---|
| **版本戳** | 期望的是「值 + 版本」一起比 | `AtomicStampedReference` / `AtomicMarkableReference` |
| **不复用危险身份** | 换新对象、或令牌不回收到可混淆状态 | 设计上避开 |
| **上锁 / 更强结构** | 临界区看完整不变量 | 冲突本就该用锁时 |

口述：ABA 不是 CAS「比错了」，而是 **「值相等」不足以代表「中间没人动过」**。

#### 3. 忙等（自旋）

CAS 失败后立刻再 `get` + `compareAndSet`，线程 **一直占着 CPU**，不进 WAITING。

代价：
- 竞争重时大量失败 → **空转烧核**，吞吐可能反不如一把锁。
- 单核 / 时间片紧张时，自旋者可能拖慢真正持有「逻辑进展」的线程。

缓解（实现层常见套路）：
- **有界自旋**：重试 N 次后 `Thread.yield()` / `LockSupport.parkNanos` / 转锁。
- **退避（backoff）**：失败后短暂暂停，降低 livelock 式互相踩踏。
- **自适应**：JVM 轻量级锁自旋就是这类思想；业务侧别无限 `while (!cas)` 包大段逻辑。

#### 4. 高竞争怎么处理

热点是 **同一个内存地址** 被很多核 CAS：缓存行乒乓（false sharing 时更糟）。

常见策略：

1. **打散计数 / 累加**：`LongAdder` / `LongAccumulator` —— 多 Cell 分散更新，读时再汇总（`ConcurrentHashMap` 的 `size` 计数同思路）。
2. **缩小共享面**：分段、分桶、线程本地缓冲再批量合并（如日志、指标）。
3. **改悲观**：临界区不短或冲突稳定高 → `synchronized` / `ReentrantLock`，让失败者睡眠而非空转。
4. **避免伪共享**：热点字段单独占缓存行（`@Contended` 等）；详见「伪共享」题。
5. **业务层限流 / 队列化**：把「全民 CAS 一个开关」改成单写多读或队列串行化写。

选型口诀：
- 冲突低、操作短 → `Atomic*` / CAS。
- 只要总量、不要每次精确中间值 → 优先 `LongAdder` 一类。
- 冲突高或逻辑复杂 → 锁更简单也更快。

### 注意

- CAS 解决的是 **单点读改写原子性**；不自动解决业务多步骤一致性，也不消除 ABA。
- 面试别只背「CPU 指令」：要能画出 **失败重试循环**，并点出 ABA、忙等、高竞争三条代价。
- 与 JMM / `volatile` 衔接：CAS 成功写带可见性；`i++` 用 `AtomicInteger` 而不是 `volatile int`。
- 与 `synchronized` 衔接：轻量级锁、CHM 空桶占位等都用 CAS；竞争升级或打散是同一套权衡。
