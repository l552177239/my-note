## 题目

`sleep`、`wait`、`join`、`park`、`yield` 的区别？

## 答案

1. **`Thread.sleep(ms)`**：当前线程休眠一段时间，进入 `TIMED_WAITING`；**不释放**已持有的监视器锁；时间到（或被中断）后继续跑。
2. **`Object.wait()`**：必须在 `synchronized` 里调用；释放对应对象的监视器，进入 `WAITING` / `TIMED_WAITING`，等 `notify` / `notifyAll`（或超时）后再**重新抢锁**。
3. **`Thread.join()`**：当前线程等待**目标线程结束**；无参 → `WAITING`，带超时 → `TIMED_WAITING`；本质是对目标线程对象做 `wait` 系等待。
4. **`LockSupport.park()`**：当前线程进入 `WAITING` / `TIMED_WAITING`；**不要求持有锁**，也**不释放**已持有的锁；需要 `unpark(Thread)`、中断或超时来唤醒；是 `Lock`、`Condition` 等并发工具的底层阻塞原语。
5. **`Thread.yield()`**：提示调度器让出当前时间片，状态仍是 `RUNNABLE`；**不保证**真的切换，也不释放锁。

### 解释与扩展

#### 1. 对照表

| 方法 | 所属 | 释放监视器锁？ | 进入状态 | 醒来条件 | 典型用途 |
|---|---|---|---|---|---|
| `sleep` | `Thread` 静态方法 | **否** | `TIMED_WAITING` | 时间到 / 被中断 | 限时暂停，与对象锁无关 |
| `wait` | `Object` 实例方法 | **是**（当前 `synchronized` 的那把） | `WAITING` / `TIMED_WAITING` | `notify`/`notifyAll` / 超时 / 中断 | 条件等待、生产者消费者 |
| `join` | `Thread` 实例方法 | 不持有目标线程锁时一般无关；实现上会 wait 目标线程 | `WAITING` / `TIMED_WAITING` | 目标线程 `TERMINATED` / 超时 | 等子线程跑完再汇总 |
| `park` | `LockSupport` 静态方法 | **否** | `WAITING` / `TIMED_WAITING` | `unpark` / 中断 / 超时 | 构建锁和同步器的底层阻塞原语 |
| `yield` | `Thread` 静态方法 | **否** | 仍是 `RUNNABLE` | 立刻可再被调度 | 暗示「我可让出 CPU」，几乎不用 |

#### 2. 各自要点

**sleep**
- 谁调用谁睡，与哪个对象无关。
- 持锁睡着：别的线程仍拿不到这把锁 → 易拖长临界区。
- 抛 `InterruptedException`；捕获后应恢复中断标记：`Thread.currentThread().interrupt()`。

**wait**
- 未持有监视器就 `wait` → `IllegalMonitorStateException`。
- 被唤醒后**不保证立刻执行**，要先再拿到同一把锁。
- 标准写法：`while (!条件) { obj.wait(); }`，防止虚假唤醒。

**join**
- `t.join()`：当前线程阻塞，直到 `t` 结束（或超时）。
- 可理解为「等某个线程的生命周期走完」，常用于主线程等 worker。

**park**
- 不要求持有任何锁，因此不会抛 `IllegalMonitorStateException`。
- 与 `unpark` 配对使用：`unpark` 可以先于 `park` 发生，给目标线程发一张“许可”，之后第一次 `park` 会立即返回。
- **不释放**当前线程已持有的任何锁；若在 `synchronized` 内 `park`，锁仍被握着。
- 可能被中断唤醒，但**不抛** `InterruptedException`；通常需要自己检查 `Thread.interrupted()`。
- 带超时版本：`parkNanos`、`parkUntil`。
- 是 `AQS`、`ReentrantLock`、`Condition`、`Semaphore` 等并发组件的底层实现基础。

**yield**
- 只是给调度器的**建议**，实现可忽略。
- 不能当同步手段；生产代码几乎不依赖它控制时序。

#### 3. 和线程状态的关系（口述串联）

```text
sleep(超时)     → TIMED_WAITING → 时间到 → RUNNABLE（锁一直握着）
wait()          → WAITING      → notify 后先抢锁（可能 BLOCKED）→ RUNNABLE
join()          → WAITING      → 目标终止 → RUNNABLE
park()          → WAITING      → unpark / 中断 / 超时 → RUNNABLE（锁一直握着）
yield()         → 仍在 RUNNABLE，只是可能让出 CPU
```

#### 4. `wait` 与 `park` 的对比

| 维度 | `Object.wait()` | `LockSupport.park()` |
|---|---|---|
| 是否必须在 `synchronized` 中 | 是 | 否 |
| 是否释放锁 | 释放监视器 | 不释放任何锁 |
| 唤醒方式 | `notify` / `notifyAll` | `unpark(Thread)` |
| 唤醒顺序 | 不保证，可能竞争锁 | 针对具体线程，许可机制更可控 |
| 中断行为 | 抛 `InterruptedException` | 不抛，需自行检查中断标记 |
| 先唤醒后等待 | 不支持，通知会丢失 | 支持，`unpark` 许可可先于 `park` |
| 典型定位 | Java 内置监视器模型 | 并发包底层阻塞原语 |

### 注意

- 面试高频对比：**sleep 不放锁，wait 放锁**；**park 也不放锁，但不要求先持有锁**。
- `wait` / `notify` 必须成对、在同一对象的 `synchronized` 上；别和 `sleep` 混着当「暂停」用。
- `park` / `unpark` 是底层工具，业务代码通常用 `Lock`、`Condition`、`BlockingQueue` 等更高层抽象。
- `join` 超时返回后要用 `isAlive()` 判断对方是否真结束。
- `yield` 不可预期，别用来「解决」竞态。
- 中断：`sleep` / `wait` / `join` 都可能抛 `InterruptedException`；`park` 会被中断唤醒但不抛异常；`yield` 不会。
