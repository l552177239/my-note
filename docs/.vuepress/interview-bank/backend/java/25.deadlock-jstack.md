## 题目

如何构造、检测、排查死锁（jstack）？

## 答案

1. **构造**：两线程以 **相反顺序** 抢两把锁（经典 `A→B` vs `B→A`），即可稳定复现互等。
2. **检测**：`jstack <pid>` / `jcmd <pid> Thread.print`；dump 末尾常有 **`Found one Java-level deadlock`**；也可用 `ThreadMXBean.findDeadlockedThreads()`、IDE / VisualVM 线程 dump。
3. **排查**：对照 dump 里线程状态（多为 **BLOCKED**）、**waiting to lock** / **locked** 的 monitor 地址，画出「谁持谁、谁等谁」的环；再回到业务统一加锁顺序或改 `tryLock`。
4. **预防**：全局一致的锁顺序、缩小临界区、`tryLock` 超时、少嵌套多把锁、避免在持锁时做不确定时长的 IO。

### 解释与扩展

#### 1. 死锁是什么（口述四条件）

循环等待资源且都不释放。充分条件常提：
1. 互斥  
2. 占有且等待  
3. 不可抢占  
4. **循环等待**

Java 里最常见：**嵌套 `synchronized` / `Lock` 顺序不一致**。

#### 2. 如何构造（面试可手写）

```java
Object a = new Object();
Object b = new Object();

Thread t1 = new Thread(() -> {
  synchronized (a) {
    sleep(100);
    synchronized (b) { /* ... */ }
  }
}, "t1");

Thread t2 = new Thread(() -> {
  synchronized (b) {
    sleep(100);
    synchronized (a) { /* ... */ }
  }
}, "t2");

t1.start();
t2.start();
```

`t1` 持 `a` 等 `b`，`t2` 持 `b` 等 `a` → 死锁。  
`ReentrantLock` 漏 `unlock`、锁顺序反了、数据库行锁互等，本质同类。

#### 3. 如何检测（jstack 主路径）

```bash
# 找 Java 进程
jps -l
# 或 ps / top

jstack <pid> > dump.txt
# 等价较新写法
jcmd <pid> Thread.print > dump.txt
```

关注：
- 文末 **`Found one Java-level deadlock:`** 及随后的线程对、锁地址。
- 线程块里：`java.lang.Thread.State: BLOCKED (on object monitor)`。
- `- waiting to lock <0x...>`（在等谁）  
- `- locked <0x...>`（已持有谁）

示例（结构示意）：

```text
Found one Java-level deadlock:
=============================
"t1":
  waiting to lock monitor 0xB (object ... , a java.lang.Object)
  which is held by "t2"
"t2":
  waiting to lock monitor 0xA ...
  which is held by "t1"

"t1":
  at Demo.run
  - waiting to lock <0xB>
  - locked <0xA>
"t2":
  - waiting to lock <0xA>
  - locked <0xB>
```

程序内自检（运维/测试可周期性打）：

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();
if (ids != null) {
  // 打日志 / 告警，再配合 jstack
}
```

#### 4. 排查步骤（现场）

1. **现象**：接口卡住、线程池打满、CPU 不高但 RT 暴涨、部分请求永不返回。  
2. **确认进程**：`jps` / 容器内 pid。  
3. **打 dump**：`jstack` / `jcmd Thread.print`（必要时隔几秒打两次对比）。  
4. **找环**：先看 deadlock 专段；没有则搜大量 `BLOCKED`，按 monitor 地址手工串环。  
5. **落到代码**：栈顶业务类 + 锁对象（常是类名/`this`），对照加锁顺序。  
6. **修复**：统一顺序（如按对象 `identityHashCode` 排序后加锁）、`tryLock(timeout)` 失败回滚已持锁、减少嵌套、拆锁粒度。

```mermaid
flowchart LR
  t1["t1 持 A 等 B"] --> t2["t2 持 B 等 A"]
  t2 --> t1
```

### 注意

- `jstack` 对 **JVM 能识别的 monitor / 部分 Lock** 较友好；纯 park、网络阻塞不一定标成「Java-level deadlock」，要靠栈与状态判断。
- 死锁 **不会** 因「等一会儿」自动解开，必须改代码或杀进程；发现后优先保留 dump 再重启。
- 预防口诀：**一把锁少嵌套；多把锁同顺序；能 tryLock 就不死等**。
- 与锁题衔接：`synchronized` / `ReentrantLock` 都会死锁；`Lock` 可用超时降低风险，但漏 `unlock` 同样致命。
