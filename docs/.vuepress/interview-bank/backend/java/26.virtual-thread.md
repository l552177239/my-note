## 题目

虚拟线程与平台线程的调度模型差异？

## 答案

1. **平台线程（Platform Thread）**：与 OS 线程大致 **1:1**；由 **操作系统调度器** 调度，创建/切换成本高，数量通常几十～几百量级。
2. **虚拟线程（Virtual Thread，Java 21 JEP 444）**：由 **JVM 调度** 的轻量用户态线程；大量虚拟线程 **M:N 复用** 到少量平台线程（**carrier**）上跑。
3. **关键差异**：平台线程阻塞 ≈ 占住一颗 OS 线程；虚拟线程在多数 JDK 可感知阻塞点会 **卸载（unmount）** carrier，让别的虚拟线程接着用这颗平台线程。
4. **适用**：虚拟线程适合 **大量阻塞式 IO** 的吞吐型任务；CPU 密集仍靠有限平台线程 / 传统池，别指望「开百万虚线程算得更快」。

### 解释与扩展

#### 1. 两种调度模型（口述图）

```text
平台线程（1:1）
  Java Thread  ←→  OS Thread  ←  OS 调度到 CPU

虚拟线程（M:N）
  VirtualThread × N
        ↕ mount / unmount
  Carrier（平台线程）× M（常 ≈ CPU 核数级 ForkJoin 池）
        ↕
  OS 调度到 CPU
```

| | 平台线程 | 虚拟线程 |
|---|---|---|
| 调度者 | OS | JVM（挂到 carrier 上跑） |
| 与 OS 线程关系 | 约 1:1 | 多对少（M:N） |
| 栈 / 元数据 | 重（通常 MB 级栈预留观感） | 轻，按需增长 |
| 规模直觉 | 有限 | 可成千上万～百万级（受堆与业务约束） |
| 阻塞时 | 整颗 OS 线程卡住 | 多数阻塞可卸载，carrier 去跑别人 |

创建方式直觉：

```java
// 平台线程（传统）
Thread.ofPlatform().start(() -> { ... });
new Thread(() -> { ... }).start();

// 虚拟线程
Thread.ofVirtual().start(() -> { ... });
Executors.newVirtualThreadPerTaskExecutor(); // 一任务一虚线程
```

#### 2. mount / unmount（虚拟线程调度核心）

1. 虚拟线程要执行时，被 **mount** 到某个 carrier（平台线程）上，在该 OS 线程里跑字节码。
2. 遇到 JDK 已适配的阻塞（如部分 IO、`LockSupport.park`、部分锁等待等），虚拟线程 **unmount**：从 carrier 卸下，状态保存；carrier 可去跑队列里别的虚线程。
3. 阻塞结束后再被调度 **重新 mount**（可能换到另一个 carrier）继续跑。

这就是「阻塞式写法、事件驱动式吞吐」的调度模型差异：**阻塞不再 equates 浪费一整颗平台线程**。

#### 3. Carrier 从哪来

- 默认虚拟线程调度器基于 **ForkJoinPool** 一类工作窃取池，并行度常与 CPU 相关（可用系统属性调，面试知「有限 carrier」即可）。
- 业务代码里的 `Thread.currentThread()` 在虚线程里返回的是 **虚拟线程自身**，不是 carrier；不要假设「当前就是某 OS 线程身份」做绑定（除非明确需要平台线程）。

#### 4. 何时仍「钉住」carrier（pinning）

虚线程在某些情况下 **不能卸载**，会把 carrier 一起占住，近似退化成贵的平台线程占用：

| 情况 | 直觉 |
|---|---|
| **`synchronized` 临界区内阻塞** | 经典 pinning 场景；长 IO 更宜用 `ReentrantLock` 等 |
| **本地方法 / 未适配的阻塞** | carrier 跟着等 |
| **长时间 CPU 计算** | 不卸载也没空给别人；虚线程帮不上算力 |

面试可补一句：JDK 持续减少 pinning；选型上 **IO 密集 + 阻塞 API** 用虚线程，**算力密集** 仍控制并行度。

#### 5. 和线程池心智的差异

| 传统平台线程池 | 虚拟线程常见用法 |
|---|---|
| 少线程 + 队列，复用工人 | **一任务一虚线程**（`newVirtualThreadPerTaskExecutor`） |
| 要精细调 core / max / 队列 / 拒绝 | 池的意义变弱；限流用信号量、隔板、结构化并发等 |
| IO 池靠「多开线程填等待」 | 虚线程把「多开」成本降下来 |

与上一题衔接：CPU/IO 估平台线程池公式仍有效；上虚线程后，IO 场景往往不再堆一个巨大 `ThreadPoolExecutor`，而是虚线程 + 有界并发（如信号量）保护下游。

### 注意

- 虚线程 **不是** 更快的 CPU；只是让「等」更便宜。纯计算别靠百万虚线程提速。
- `ThreadLocal` 在虚线程上仍可用，但百万任务 × 大对象 ThreadLocal 会放大内存；优先靠参数传递 / 结构化并发作用域。
- 不要把虚线程再丢进会池化、长期占用的旧平台线程池模型里硬套；也不要在虚线程里再搞大平台线程池嵌套。
- 取舍与不适用场景见下一题「虚拟线程与线程池如何取舍」。
- 面试加分：说清 **M:N + mount/unmount**，并点出 **`synchronized` pinning**。
