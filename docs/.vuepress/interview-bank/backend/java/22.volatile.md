## 题目

volatile 能保证什么、不能保证什么？

## 答案

1. **能保证**：**可见性**（写对后续读立即可见）+ **有序性**（禁止该变量相关的有害重排；写 HB 后续读）。
2. **不能保证**：**复合操作的原子性**（如 `i++`、`check-then-act`）；也不提供互斥，多写者仍可能交错。
3. **适用场景**：一写多读的状态标志、DCL 中的实例引用、安全发布不可变 / 已写完的状态；需要读改写或临界区时用锁 / 原子类。

### 解释与扩展

#### 1. 能保证什么

| 保证 | 含义 | happens-before / 直觉 |
|---|---|---|
| **可见性** | 线程 A 对 `volatile` 变量的写，对之后任意线程的读可见 | 写 HB 随后对该变量的读；读时不会一直停在过期缓存副本 |
| **有序性** | 与该 `volatile` 读写相关的重排受限 | 写之前的普通写不能排到该 `volatile` 写之后；读之后的普通读不能排到该 `volatile` 读之前（屏障语义的面试说法） |

典型用法：

```java
// 状态标志：写方改完业务数据后，再写 volatile 标志
volatile boolean ready;
// 线程 A
data = 42;      // 普通写
ready = true;   // volatile 写：前面的 data 写对读到 ready==true 的线程可见

// 线程 B
if (ready) {    // volatile 读
  use(data);    // 能看到 42
}
```

双重检查锁（DCL）里实例字段要 `volatile`，防止「先发布引用、后写构造字段」的重排，避免读到半初始化对象。

#### 2. 不能保证什么

| 不能保证 | 原因 | 反例 |
|---|---|---|
| **`i++` 等读改写原子性** | `i++` = 读 → 加一 → 写，三步可交错；`volatile` 只保证每步读写的可见/有序，不合并成一步 | 两线程同时 `count++`，结果仍可能少加 |
| **check-then-act** | 「先读再决定再写」中间无互斥 | `if (singleton == null) singleton = new ...` 无锁仍会创建多个 |
| **互斥 / 临界区** | 不阻塞其他线程，不能当锁用 | 多写者同时改结构，仍需 `synchronized` / `Lock` |

```java
volatile int count = 0;
count++; // ❌ 仍然线程不安全，要用 AtomicInteger 或加锁
```

#### 3. 和 synchronized / 原子类怎么选

| 手段 | 可见性 | 有序性 | 原子性（复合操作） | 代价直觉 |
|---|---|---|---|---|
| `volatile` | ✓ | ✓（对该变量） | ✗ | 轻；无阻塞 |
| `synchronized` / `Lock` | ✓ | ✓ | ✓（临界区内） | 互斥；可能阻塞 |
| `Atomic*` | ✓（字段语义） | ✓ | ✓（CAS 单变量） | 无锁争用好，争用重则重试 |

口述收束：`volatile` = **轻量的可见性 + 有序性开关**，不是轻量锁。

### 注意

- 面试高频坑：说「`volatile` 保证原子性」——错；至多说「单次读/写对该类型是原子的」，**复合操作不行**。
- `long` / `double`：`volatile` 保证其读写在 JMM 下也不拆成两半可见（与「非 volatile 的 64 位写」老问题对照时常被问到）。
- 一写多读最合适；多写且写之间有依赖 → 锁或原子类。
- 与 JMM 题衔接：三大特性里 `volatile` 覆盖可见性 + 有序性，原子性留给锁 / CAS。
