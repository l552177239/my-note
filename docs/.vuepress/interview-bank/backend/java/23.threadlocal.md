## 题目

ThreadLocal 原理？为什么可能内存泄漏？★

## 答案

1. **作用**：为每个线程提供一份独立的变量副本，避免共享可变状态；典型场景：用户上下文、事务 / 连接绑定、SimpleDateFormat、MDC。
2. **原理**：每个 `Thread` 持有一个 `ThreadLocalMap`；`ThreadLocal` 本身只是 key，真正存的是「当前线程 map 里该 key 对应的 value」。
3. **内存泄漏风险**：`Entry` 的 key 是对 `ThreadLocal` 的 **弱引用**，value 是 **强引用**。`ThreadLocal` 被回收后 key 变 `null`，value 仍挂在线程上；线程池里线程长期存活时，脏 Entry / 大对象更难被回收。
4. **规避**：用完务必 `remove()`（`finally`）；线程池场景尤其要清。

### 解释与扩展

#### 1. 原理（数据存在哪）

```text
Thread t
  └─ threadLocals: ThreadLocalMap
        └─ Entry[] table
              Entry: key = WeakReference<ThreadLocal<?>>
                     value = 业务对象（强引用）
```

- `tl.set(v)` → 取当前线程的 `ThreadLocalMap`，以 `tl` 为 key 写入 `v`。
- `tl.get()` → 同一线程 map 里按 `tl` 取；没有则走 `initialValue()`。
- **不是**「一个 ThreadLocal 里 map 存很多线程」，而是「每个线程一个 map，key 是各个 ThreadLocal」。

口述口诀：**Thread 持有 Map，ThreadLocal 当 key，value 才是副本**。

#### 2. 为什么用弱引用做 key

若 key 也是强引用：即使业务代码已不再引用某个 `ThreadLocal` 静态/实例，只要线程还活着，Entry 就会一直拦住 `ThreadLocal` 对象本身无法回收。

做成 **弱引用 key** 后：没有强引用指向该 `ThreadLocal` 时，下次 GC 可回收 key；map 在 `get` / `set` / `remove` 时还会清理 key 已为 `null` 的脏 Entry（expunge）。

#### 3. 为什么仍可能「泄漏」

弱引用只救了 **key（ThreadLocal 对象）**，没救 **value**：

| 条件 | 结果 |
|---|---|
| `ThreadLocal` 已无强引用，被 GC | Entry.key → `null`（脏槽） |
| Entry.value 仍是强引用 | 大对象 / 连接等仍被 **Thread → Map → Entry → value** 链住 |
| 线程很快结束 | 整条链随线程一起可回收，问题不明显 |
| **线程池复用长生命周期线程** | 脏 Entry / value 长期挂着 → 堆涨、假泄漏 |

再叠加：若从不触发带清理逻辑的 `get`/`set`/`remove`，脏 Entry 清理也会推迟。

典型坑：在线程池 worker 里 `set` 了用户上下文 / DB 连接包装，请求结束没 `remove` → 下次复用同线程读到脏数据，且对象迟迟不释放。

```java
try {
  USER_CTX.set(user);
  // 业务
} finally {
  USER_CTX.remove(); // 必须
}
```

#### 4. 和 InheritableThreadLocal / 传递性

- 普通 `ThreadLocal`：**子线程不继承**父线程的值。
- `InheritableThreadLocal`：创建子线程时拷贝父 map 中可继承的项；**线程池提交任务时父线程往往已不是创建线程的那次**，一般传不下去，要用 TransmittableThreadLocal 一类方案（面试点到即可）。

### 注意

- 泄漏本质是 **Thread → Map → value 的强引用链 + 线程池长寿**，不是「弱引用导致泄漏」；弱引用是缓解 key 回收的设计，value 仍靠 `remove`。
- 静态 `ThreadLocal` 常见且合理（作为 key 长期存活）；真正要清的是 **每个线程上的 value**。
- 面试加分：能画出 Thread / Map / WeakReference key / 强引用 value，并点出线程池场景。
- 与 MDC、请求上下文题衔接：框架也基于 ThreadLocal，过滤器 / 拦截器里同样要 `clear` / `remove`。
