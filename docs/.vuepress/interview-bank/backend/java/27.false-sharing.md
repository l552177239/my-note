## 题目

什么是伪共享？产生原因与解决方案？

## 答案

1. **伪共享（False Sharing）**：多个线程写的是 **不同变量**，但这些变量落在 **同一缓存行（cache line）** 上，导致缓存行在多核间不断失效 / 来回传递，性能像「真共享」一样差。
2. **产生原因**：CPU 以 **缓存行**（常见 64B）为一致性单位；行内任一字节被某核改写，其他核上该行副本常需 **失效（如 MESI）**——逻辑上无共享，物理上「行共享」。
3. **解决**：让热点写字段 **独占缓存行**——填充（padding）、`@Contended`、打散到不同对象 / 数组槽；或减少多核同时写相邻热点（改分段计数如 `LongAdder`）。
4. **何时管**：高并发、多核对相邻字段狂写（计数器数组、环形队列游标旁的元数据）才值得优化；普通业务别先上 padding。

### 解释与扩展

#### 1. 是什么（对比真共享）

| | 真共享 | 伪共享 |
|---|---|---|
| 写的对象 | 同一变量 / 同一锁保护的状态 | **不同** 变量 |
| 为何慢 | 正确性需要同步；缓存也要一致性 | 变量无关，却因 **同属一行** 触发一致性流量 |
| 直觉 | 抢同一把锁 / 同一计数 | 两人改不同座位，却因「同一排桌子」整桌被搬走重拿 |

示意（一行 64B，两 `long` 相邻）：

```text
同一 cache line（约 64B）
┌──────────┬──────────┬──────────┐
│  x (8B)  │  y (8B)  │  ...     │
└──────────┴──────────┴──────────┘
   ↑ 核A写              ↑ 核B写
   → 整行在 A/B 的 L1 间乒乓失效
```

#### 2. 产生原因（硬件 + 布局）

1. **缓存行是一致性粒度**：核不按「单个 int」做一致性，而按整行。
2. **对象 / 数组字段紧密排布**：JVM 把相邻字段、数组相邻元素放在连续地址 → 极易进同一行。
3. **多核并行写**：线程绑定不同核，各自改「自己的」计数器 / 游标，但仍踢对方缓存。
4. **读多写少通常不惨**：伪共享杀伤主要在 **多写者**；只读共享行代价小得多。

典型代码形态：

```java
// 危险直觉：每线程写自己的 slot，却可能伪共享
static class Counters {
  long c0, c1, c2, c3; // 很可能挤在同一或相邻 cache line
}

// 环形缓冲区：head / tail 相邻也常见
class Ring {
  long head;
  long tail; // 与 head 同对象、常相邻 → 生产/消费核互踢
}
```

#### 3. 解决方案

| 手段 | 做法 | 说明 |
|---|---|---|
| **填充 padding** | 在热点字段前后塞 `long p0..p6` 等，凑满一行 | 手动、易碎（压缩、字段重排） |
| **`@Contended`** | `jdk.internal.vm.annotation.Contended`（旧 `sun.misc`）给字段/类加独占填充 | 需开启相关选项（如 `-XX:-RestrictContended` 视版本）；JDK 内部（如 `ForkJoinPool`、`Thread` 部分字段）已用 |
| **独立对象 / 数组间隔** | 每线程一个对象；或数组下标 stride（隔多个元素） | 用「空间换行独占」 |
| **打散写热点** | `LongAdder` / `LongAccumulator`、CHM 的 CounterCell | 减少多核写同一行，顺带降 CAS 争用 |
| **结构重排** | 把「只读」与「狂写」、或两狂写字段拆开 | 生产/消费游标分开放 |

填充示意：

```text
┌─ padding ─┬─ hot ─┬─ padding ─┐  ≈ 独占一行
│  空字节    │  x    │  空字节    │
└───────────┴───────┴───────────┘
```

```java
@Contended
volatile long value; // 意图：周围留白，降低与邻字段伪共享
```

#### 4. 怎么发现、何时优化

- 症状：多核吞吐上不去，CPU 不低，但扩展比核数差；profiler 难直接显示「伪共享」，常靠 **对照实验**（加 padding / `@Contended` 后吞吐跳变）。
- 工具向：性能计数器看 cache line 失效 / false sharing 相关事件（平台相关）；面试说到「猜布局 + 压测验证」即可。
- **先别全局 padding**：浪费 L1，对象变大；只处理已证实的热点写路径。

### 注意

- 伪共享是 **性能问题**，不是正确性 bug；程序结果可以一直对，只是慢。
- 字段重排、压缩 oops、不同 CPU 行宽（多为 64B，不绝对）会让「手写 padding」失效，优先 `@Contended` 或官方分段结构。
- 与 CAS / `LongAdder` 题衔接：高竞争时既有原子争用，也可能叠加伪共享；打散写往往一举两得。
- 面试加分：能画出「同行不同字段 + MESI 失效」，并说出 padding / `@Contended` / Adder 三条解法。
