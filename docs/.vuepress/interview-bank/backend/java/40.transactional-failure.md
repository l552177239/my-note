## 题目

@Transactional 注解常见的失效场景及解决方案？

## 答案

常见失效：① 同类内部自调用；② 方法非 `public`；③ 异常被吃掉或抛检查异常未配 `rollbackFor`；④ 数据库/引擎不支持事务；⑤ Bean 未被 Spring 管理；⑥ 传播行为用错；⑦ 多数据源事务管理器未指定。

对应解法：自注入/拆 Bean/`AopContext`；改 public；正确抛出或配置回滚；确认 InnoDB 等；保证组件扫描；核对传播与 `TransactionManager`。

### 解释与扩展

#### 1. 失效场景清单

| 场景 | 原因 | 解决 |
|---|---|---|
| `this.xxx()` 自调用 | 不走代理 | 拆分到另一 Bean；注入自身；`AopContext.currentProxy()` |
| `private` / `protected` | Spring 基于代理的事务默认只拦 public | 改为 public，或改用 AspectJ 模式 |
| `catch` 后不抛 | 拦截器以为成功 | 回抛，或 `setRollbackOnly` |
| 抛 `Exception`（检查异常） | 默认只回滚 Runtime/Error | `@Transactional(rollbackFor = Exception.class)` |
| 非 Spring Bean | 无代理 | `@Service` 等 + 扫描 |
| 方法调到只读库/非事务引擎 | 底层无事务 | MyISAM→InnoDB；检查数据源 |
| 错误的传播 | 如 `NOT_SUPPORTED` | 按业务改传播 |
| 多 TM 未指定 | 绑错管理器 | `transactionManager = "..."` |

#### 2. 自调用示意

```java
@Service
public class OrderService {
  public void place() {
    this.save(); // 失效：this 不是代理
  }
  @Transactional
  public void save() { ... }
}
```

#### 3. 排查顺序（面试加分）

先确认 **是否进入 TransactionInterceptor**（日志/断点）→ 再看异常类型与回滚规则 → 再看数据源与隔离。

### 注意

- 「加了注解就有事务」是错觉；本质是 **代理 + 拦截器 + 事务管理器**。
- 与「内部调用 / 非 public 底层原因」题可合并准备。
